# Communication Transport Overview

HORUS uses **local shared memory** as its transport mechanism, providing ultra-low latency IPC for nodes running on the same machine.

## Transport: Shared Memory

**What**: Shared memory regions under `/dev/shm/horus/` (Linux) or equivalent (macOS/Windows)
**When**: All nodes running on the same computer (same-process or cross-process)
**Latency**: Ultra-fast (~3ns same-thread to ~167ns cross-process MPMC)

```rust
// All topics use shared memory automatically
let topic: Topic<SensorData> = Topic::new("sensors")?;
let imu: Topic<ImuData> = Topic::new("imu.data")?;
```

**How it works**:
- Memory-mapped regions in RAM accessible by all processes
- Zero-copy for POD (Plain Old Data) types
- Lock-free atomic operations
- Cache-aligned for performance

## Automatic Backend Selection

HORUS automatically selects the optimal backend based on how many publishers and subscribers exist and whether they're in the same process:

| Backend | Latency | Description |
|---------|---------|-------------|
| **DirectChannel** | ~3ns | Same thread, publisher and subscriber in one node |
| **SpscIntra** | ~18ns | Same process, 1 publisher, 1 subscriber |
| **SpmcIntra** | ~24ns | Same process, 1 publisher, multiple subscribers |
| **MpscIntra** | ~26ns | Same process, multiple publishers, 1 subscriber |
| **MpmcIntra** | ~36ns | Same process, multiple publishers and subscribers |
| **PodShm** | ~50ns | Cross-process, POD type (fastest cross-process) |
| **MpscShm** | ~65ns | Cross-process, multiple publishers, 1 subscriber |
| **SpmcShm** | ~70ns | Cross-process, 1 publisher, multiple subscribers |
| **SpscShm** | ~85ns | Cross-process, 1 publisher, 1 subscriber |
| **MpmcShm** | ~167ns | Cross-process, multiple publishers and subscribers |

You don't need to choose a backend — HORUS selects the fastest one automatically based on the actual usage pattern.

## Performance

### Latency by Message Size

| Message Size | SPSC (cross-process) | MPMC (cross-process) |
|-------------|---------------------|---------------------|
| Small (&lt;1KB) | ~85ns | ~167ns |
| Medium (1-10KB) | 500ns-2µs | 1-4µs |
| Large (100KB+) | 5-20µs | 10-40µs |

Latency scales linearly with message size.

### Throughput

- **SPSC**: 2.5M+ msgs/sec (small messages)
- **MPMC**: 1.5M+ msgs/sec (small messages)
- Limited by memory bandwidth, not synchronization

### Frequency Guidelines

- **10kHz** (100µs period): Plenty of headroom with ~85ns latency
- **1kHz** (1ms period): Typical control loop rate
- **100Hz** (10ms period): Sensor fusion, planning
- **30Hz** (33ms period): Camera, visualization

## When to Use Local Transport

**Single-machine systems**
```rust
// Raspberry Pi robot with multiple processes
let camera: Topic<Image> = Topic::new("camera")?;
let motors: Topic<MotorCmd> = Topic::new("motors")?;
```

**Development and testing**
```bash
# All nodes on your laptop
horus run sensors.rs &
horus run controller.rs &
horus run motors.rs &
```

**Ultra-low latency requirements**
```rust
// 1kHz control loop (1ms period)
// ~85ns SPSC latency leaves plenty of headroom
let state: Topic<State> = Topic::new("state")?;
```

**High-bandwidth data**
```rust
// Streaming 30 FPS camera at 1920x1080
let camera: Topic<Image> = Topic::new("camera")?;
```

### Benefits

- **Fastest possible**: ~3ns-~167ns latency depending on backend
- **Zero-copy**: No serialization overhead for POD types
- **Deterministic**: Predictable, no network jitter
- **Simple**: No network configuration needed
- **Reliable**: No packet loss or connection issues
- **Automatic**: Backend selected automatically based on usage pattern

### Limitations

- **Same machine only**: All nodes must run on same computer
- **Limited by RAM**: Shared memory uses system RAM
- **No fault isolation**: If machine crashes, all nodes down

## Topic Configuration

### Custom Capacity

```rust
// Create topic with custom capacity (number of message slots)
let topic: Topic<SensorData> = Topic::with_capacity("sensors", 32, None)?;
```

## Reliability

### Shared Memory Guarantees

**Pros**:
- No packet loss
- No connection failures
- Deterministic latency
- No network jitter

**Cons**:
- All nodes must be on same machine
- Shared fate (machine crash kills everything)

### Best Practices

**For critical systems**:
- Use shared memory for all critical control loops
- Use appropriate backend capacity for your message rate
- Monitor topic health with `horus monitor`

## Network Discovery (mDNS)

HORUS includes **mDNS/DNS-SD** support (behind the `mdns` feature flag) for zero-configuration node discovery on the local network:

```rust
use horus::prelude::*;

// Discover HORUS nodes on the network
let nodes = discover()?;
for node in &nodes {
    println!("Found node: {} at {}", node.name, node.ip);
}
```

mDNS allows nodes to discover each other without hardcoding IP addresses. This is useful for monitoring and debugging distributed setups, though topic data transport remains local shared memory.
