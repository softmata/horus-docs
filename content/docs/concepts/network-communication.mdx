# Network Communication

HORUS supports network communication for building distributed systems across multiple machines. Topic work transparently over the network with only a syntax change.

## Quick Start

### Topic Network Example

```rust
// === MACHINE 1 (Producer @ 192.168.1.10) ===
use horus::prelude::*;

// Connect to consumer at 192.168.1.20:9000
let output: Topic<SensorData> = Topic::new("sensors@192.168.1.20:9000")?;
output.send(data)?;

// === MACHINE 2 (Consumer @ 192.168.1.20) ===
use horus::prelude::*;

// Listen for producer on port 9000
let input: Topic<SensorData> = Topic::new("sensors@0.0.0.0:9000")?;
if let Some(data) = input.recv() {
    process(data);
}
```

### Topic Network Example

```rust
// === MACHINE 1 (Publisher @ 192.168.1.10) ===
use horus::prelude::*;

// Publish to network
let pub_topic: Topic<Status> = Topic::new("status@192.168.1.20")?;
pub_topic.send(status)?;

// === MACHINE 2 (Subscriber @ 192.168.1.20) ===
use horus::prelude::*;

// Subscribe from network
let sub_topic: Topic<Status> = Topic::new("status@192.168.1.20")?;
if let Some(status) = sub_topic.recv() {
    process(status);
}
```

### Python Examples

The same endpoint syntax works in Python:

**Topic (Python):**
```python
from horus import Topic, SensorData

# === MACHINE 1 (Producer) ===
output = Topic(SensorData, endpoint="sensors@192.168.1.20:9000")
output.send(data)

# === MACHINE 2 (Consumer) ===
input_link = Topic(SensorData, endpoint="sensors@0.0.0.0:9000")
if msg := input_link.recv():
    process(msg)
```

**Topic (Python):**
```python
from horus import Topic, Status

# Network topic with endpoint parameter
topic = Topic(Status, endpoint="status@192.168.1.20:8000")
topic.send(status)

# Receive
if msg := topic.recv():
    process(msg)
```

**Router (Python):**
```python
from horus import Topic, RouterClient, CmdVel

# Method 1: Implicit router endpoint
router_topic = Topic(CmdVel, endpoint="cmdvel@router")

# Method 2: Explicit RouterClient
router = RouterClient("192.168.1.100", 7777)
topic = Topic(CmdVel, endpoint=router.endpoint("cmdvel"))
```

See [Python Bindings - Network Communication](/python/api/python-bindings#network-communication) for full Python documentation.

## Endpoint Syntax

HORUS uses a simple `topic@address` syntax to specify network endpoints:

### Topic Endpoints (TCP)

**Producer (connects to consumer)**:
```rust
Topic::new("topic@192.168.1.20:9000")?     // Connect to specific IP:port
Topic::new("topic@hostname:9000")?         // Connect to hostname
Topic::new("topic@drone.local:9000")?      // mDNS/Avahi hostname
```

**Consumer (listens for producer)**:
```rust
Topic::new("topic@0.0.0.0:9000")?          // Listen on port 9000 (all interfaces)
Topic::new("topic@192.168.1.20:9000")?     // Listen on specific interface
```

### Topic Endpoints (UDP)

```rust
Topic::new("topic@192.168.1.20")?                // Direct UDP (default port)
Topic::new("topic@192.168.1.20:8000")?           // Direct UDP (custom port)
Topic::new("topic@localhost")?                    // Unix socket (localhost optimization)
Topic::new("topic@router")?                       // Router backend (WAN/NAT traversal)
```

### Local Endpoints (Shared Memory)

```rust
// No '@' symbol = local shared memory
Topic::new("topic")?
Topic::new("topic")?
Topic::new("topic")?
```

## Network Backends

### Topic (SPSC): DirectBackend (TCP)

**Technology**: TCP with `TCP_NODELAY`
**Latency**: 5-15µs
**Pattern**: Point-to-point (1 producer → 1 consumer)

**Architecture**:
- Async Tokio I/O (event-driven, non-blocking)
- Lock-free crossbeam channels (send/recv queues)
- Buffer pooling (zero-allocation sends)
- Binary serialization (bincode)

**When to use**:
- Point-to-point communication between exactly 2 machines
- Control loops where 5-15µs latency is acceptable
- Latest-value semantics (sensor data, state updates)
- Guaranteed delivery and ordering (TCP reliability)

**Example**:
```rust
// Robot sends IMU data to ground station
// Robot (192.168.1.50)
let imu_output: Topic<ImuData> = Topic::new("imu@192.168.1.100:9000")?;

// Ground station (192.168.1.100)
let imu_input: Topic<ImuData> = Topic::new("imu@0.0.0.0:9000")?;
```

### Topic (MPMC): UdpDirectBackend (UDP)

**Technology**: UDP with packet fragmentation
**Latency**: &lt;50µs
**Pattern**: Many-to-many pub/sub

**Architecture**:
- UDP sockets (connectionless)
- Mutex-protected receive queues
- Packet fragmentation for large messages
- Polling with 100µs sleep

**When to use**:
- Broadcasting to multiple subscribers over network
- Pub/sub patterns (many publishers, many subscribers)
- Occasional packet loss acceptable
- Lower overhead than TCP

**Example**:
```rust
// Multiple robots publish position, central server aggregates
// Robot 1
let pos_pub: Topic<Position> = Topic::new("positions@192.168.1.100")?;

// Robot 2
let pos_pub: Topic<Position> = Topic::new("positions@192.168.1.100")?;

// Central server
let positions: Topic<Position> = Topic::new("positions@0.0.0.0:8000")?;
```

## Performance Characteristics

### Latency Comparison

| Transport | Topic (SPSC) | Topic (MPMC) | Speedup |
|-----------|-------------|------------|---------|
| **Local SHM** | ~85ns | ~167ns | Baseline |
| **Network** | 5-15µs | &lt;50µs | **Topic SPSC 3-10x faster** |

**Why Topic SPSC is faster on network**:
1. **Lock-free channels** (no mutex contention) vs mutex-protected queues
2. **Event-driven I/O** (async Tokio) vs polling with 100µs sleep
3. **TCP_NODELAY** (sends immediately) vs UDP overhead
4. **Buffer pooling** (zero allocations) vs standard allocations

### Message Size Impact

| Message Size | SPSC Latency | MPMC Latency |
|--------------|-------------|-------------|
| 16 bytes | 5µs | 10µs |
| 256 bytes | 8µs | 15µs |
| 1KB | 12µs | 25µs |
| 10KB | 50µs | 100µs |
| 100KB | 500µs | 1ms |

**Note**: Network latency dominated by RTT for small messages, bandwidth for large messages.

### Frequency Guidelines

**Topic Network** (5-15us latency):
- 1kHz (1ms period): Possible with headroom
- 500Hz (2ms period): Comfortable
- 100Hz (10ms period): Plenty of headroom

**Topic Network** (&lt;50us latency):
- 100Hz (10ms period): Comfortable
- 50Hz (20ms period): Safe
- 30Hz (33ms period): Typical for camera streams

## Multi-Machine Topologies

### 1. Robot Fleet Coordination

```rust
// === ROBOT 1 (192.168.1.10) ===
struct Robot1 {
    // Publish own position
    position_pub: Topic<Position>,

    // Subscribe to fleet positions
    fleet_positions: Topic<Position>,

    // Local control loop (ultra-fast)
    imu_link: Topic<ImuData>,
    motors_link: Topic<MotorCmd>,
}

impl Robot1 {
    fn new() -> Result<Self> {
        Ok(Self {
            position_pub: Topic::new("fleet.positions@router")?,
            fleet_positions: Topic::new("fleet.positions@router")?,
            imu_link: Topic::new("imu")?,      // Local
            motors_link: Topic::new("motors")?, // Local
        })
    }
}

// === ROBOT 2 (192.168.1.20) ===
// Same structure, different IP
```

### 2. Edge Computing Pipeline

```rust
// === EDGE DEVICE (192.168.1.50) - Raspberry Pi ===
struct EdgeSensor {
    // Capture camera locally
    camera: Topic<RawImage>,

    // Send to processing server
    image_output: Topic<RawImage>,
}

impl EdgeSensor {
    fn new() -> Result<Self> {
        Ok(Self {
            camera: Topic::new("camera")?,  // Local
            image_output: Topic::new("images@192.168.1.100:9000")?, // Network
        })
    }
}

// === PROCESSING SERVER (192.168.1.100) - Powerful GPU ===
struct ProcessingServer {
    // Receive from edge device
    image_input: Topic<RawImage>,

    // Process and send results back
    detections_output: Topic<Detections>,
}

impl ProcessingServer {
    fn new() -> Result<Self> {
        Ok(Self {
            image_input: Topic::new("images@0.0.0.0:9000")?,          // Network listen
            detections_output: Topic::new("detect@192.168.1.50:9001")?, // Send back
        })
    }
}
```

### 3. Distributed Sensing Network

```rust
// === SENSOR NODE 1 (192.168.1.51) ===
let temp1: Topic<Temperature> = Topic::new("temps@192.168.1.100")?;

// === SENSOR NODE 2 (192.168.1.52) ===
let temp2: Topic<Temperature> = Topic::new("temps@192.168.1.100")?;

// === SENSOR NODE 3 (192.168.1.53) ===
let temp3: Topic<Temperature> = Topic::new("temps@192.168.1.100")?;

// === AGGREGATOR (192.168.1.100) ===
let temps: Topic<Temperature> = Topic::new("temps@0.0.0.0:8000")?;
// Receives from all sensor nodes
```

### 4. Drone with Ground Control Station

```rust
// === DRONE (192.168.1.50) ===
struct Drone {
    // Local: Critical flight control (ultra-fast)
    imu: Topic<ImuData>,
    motors: Topic<MotorCmd>,

    // Network: Telemetry to GCS
    telemetry: Topic<DroneStatus>,

    // Network: Commands from GCS
    commands: Topic<Command>,
}

impl Drone {
    fn new() -> Result<Self> {
        Ok(Self {
            imu: Topic::new("imu")?,          // Local: ~85ns
            motors: Topic::new("motors")?,     // Local: ~85ns
            telemetry: Topic::new("telem@192.168.1.100")?,   // Network: &lt;50µs
            commands: Topic::new("cmd@0.0.0.0:8001")?,       // Network listen
        })
    }
}

// === GROUND CONTROL STATION (192.168.1.100) ===
struct GroundStation {
    telemetry_sub: Topic<DroneStatus>,
    command_pub: Topic<Command>,
}

impl GroundStation {
    fn new() -> Result<Self> {
        Ok(Self {
            telemetry_sub: Topic::new("telem@0.0.0.0:8000")?,  // Listen for drone
            command_pub: Topic::new("cmd@192.168.1.50:8001")?, // Send to drone
        })
    }
}
```

## Network Configuration

### Using Configuration Files

Instead of hardcoding IP addresses, use configuration files:

**horus.yaml** (production):
```yaml
topics:
  telemetry:
    name: telemetry
    endpoint: telemetry@192.168.1.100:8000

  camera:
    name: camera
    endpoint: camera@192.168.1.50:9000
```

**horus_dev.yaml** (development):
```yaml
topics:
  telemetry:
    name: telemetry
    endpoint: telemetry  # Local for testing

  camera:
    name: camera
    endpoint: camera  # Local for testing
```

**Code** (same for dev and prod):
```rust
// Automatically loads from horus.yaml or horus_dev.yaml
let telemetry: Topic<Status> = Topic::from_config("telemetry")?;
let camera: Topic<Image> = Topic::from_config("camera")?;
```

See [Communication Configuration](/concepts/communication-configuration) for details.

### Environment-Specific Endpoints

```bash
# Development (local)
export HORUS_CONFIG=horus_dev.yaml
horus run robot.rs

# Production (network)
export HORUS_CONFIG=horus.yaml
horus run --release robot.rs
```

## Error Handling

### Connection Failures

```rust
use horus::prelude::*;

let link: Topic<Data> = match Topic::new("data@192.168.1.100:9000") {
    Ok(l) => l,
    Err(e) => {
        eprintln!("Failed to connect: {}", e);
        // Retry or fallback to local mode
        Topic::new("data")?
    }
};
```

### Timeouts and Heartbeats

```rust
struct NetworkNode {
    data_link: Topic<SensorData>,
    last_recv: std::time::Instant,
}

impl Node for NetworkNode {
    fn tick(&mut self) {
        if let Some(data) = self.data_link.recv() {
            self.last_recv = std::time::Instant::now();
            self.process(data);
        } else {
            // Check for timeout
            if self.last_recv.elapsed() > std::time::Duration::from_secs(5) {
                hlog!(error, "Network timeout - no data received for 5s");
            }
        }
    }
}
```

### Graceful Degradation

```rust
struct RobotWithFallback {
    // Try network first
    telemetry_network: Option<Topic<Status>>,

    // Fallback to local logging
    telemetry_local: Topic<Status>,
}

impl Node for RobotWithFallback {
    fn tick(&mut self) {
        let status = self.get_status();

        // Try network first
        if let Some(ref net) = self.telemetry_network {
            if net.send(status.clone()).is_ok() {
                return;  // Success!
            }
        }

        // Fallback to local logging
        self.telemetry_local.send(status).ok();
    }
}
```

## Network Performance Tuning

### 1. TCP Buffer Sizes

For high-throughput Topic connections:

```bash
# Increase TCP buffer sizes (Linux)
sudo sysctl -w net.core.rmem_max=16777216
sudo sysctl -w net.core.wmem_max=16777216
sudo sysctl -w net.ipv4.tcp_rmem="4096 87380 16777216"
sudo sysctl -w net.ipv4.tcp_wmem="4096 65536 16777216"
```

### 2. UDP Buffer Sizes

For high-rate Topic pub/sub:

```bash
# Increase UDP buffer sizes
sudo sysctl -w net.core.rmem_default=8388608
sudo sysctl -w net.core.wmem_default=8388608
```

### 3. Disable WiFi Power Saving

For reliable latency on WiFi:

```bash
# Disable WiFi power saving
sudo iw dev wlan0 set power_save off
```

### 4. QoS and Traffic Shaping

Prioritize HORUS traffic:

```bash
# Mark HORUS packets with DSCP (Differentiated Services Code Point)
sudo iptables -t mangle -A OUTPUT -p tcp --dport 9000 -j DSCP --set-dscp 46
sudo iptables -t mangle -A OUTPUT -p udp --dport 8000 -j DSCP --set-dscp 46
```

## Firewall Configuration

### Linux (ufw)

```bash
# Allow HORUS ports
sudo ufw allow 8000:9999/tcp  # Topic (TCP)
```

### Linux (iptables)

```bash
# Allow inbound HORUS traffic
sudo iptables -A INPUT -p tcp --dport 9000 -j ACCEPT
```

## Troubleshooting

### Connection Refused

**Symptom**: `Failed to connect: connection refused`

**Causes**:
1. Consumer not running yet
2. Firewall blocking port
3. Wrong IP address or port

**Solutions**:
```bash
# Check if consumer is listening
ss -tulpn | grep :9000

# Check firewall
sudo ufw status
sudo iptables -L

# Test connectivity
nc -zv 192.168.1.100 9000
```

### High Latency

**Symptom**: Network latency >100µs (expected 5-50µs)

**Causes**:
1. WiFi congestion or power saving
2. Network switch buffering
3. CPU overload

**Solutions**:
```bash
# Measure ping latency
ping -i 0.001 192.168.1.100  # 1ms interval

# Check network interface stats
ip -s link show eth0

# Disable WiFi power save
sudo iw dev wlan0 set power_save off
```

### Packet Loss

**Symptom**: Topic messages missing (UDP)

**Causes**:
1. Network congestion
2. UDP buffers too small
3. WiFi interference

**Solutions**:
```bash
# Check packet loss
ping -c 100 192.168.1.100

# Increase UDP buffers
sudo sysctl -w net.core.rmem_default=8388608

# Check WiFi signal
iwconfig wlan0
```

## Best Practices

**Use Topic for critical paths**
```rust
// Critical control loop: Topic over network
let motors: Topic<MotorCmd> = Topic::new("motors@robot:9000")?;
```

**Use Topic for broadcasting**
```rust
// Status to multiple subscribers: Topic
let status: Topic<Status> = Topic::new("status@monitoring:8000")?;
```

**Keep critical loops local**
```rust
// Flight control stays on-board (local)
let imu: Topic<ImuData> = Topic::new("imu")?;  // ~85ns, not network
```

**Use configuration files**
```rust
// Don't hardcode IPs
let telem: Topic<Status> = Topic::from_config("telemetry")?;
```

**Handle network failures**
```rust
if telemetry.send(status).is_err() {
    hlog!(warn, "Telemetry unavailable");
    // Continue operating locally
}
```

**Avoid using network for 10kHz loops**
```rust
// This won't work - network latency too high
// Use local shared memory instead
```

**Don't ignore send errors**
```rust
telemetry.send(status).ok();  // Bad! Silently fails
```

## Summary

**Topic Network** (TCP, 5-15µs):
- Point-to-point (1P1C)
- 3-10x faster than Topic MPMC network
- Reliable (TCP)
- Use for: Critical paths, control loops, pipelines

**Topic Network** (UDP, &lt;50µs):
- Many-to-many (pub/sub)
- Flexible, dynamic topologies
- Connectionless (UDP)
- Use for: Broadcasting, monitoring, coordination

**Both support**:
- Simple endpoint syntax (`topic@IP:port`)
- Transparent fallback to local
- Configuration file support
- Same API as local shared memory
