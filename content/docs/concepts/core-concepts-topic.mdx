# Topics — Full Reference

A self-driving forklift has a LiDAR scanning at 10 Hz, cameras streaming 30 FPS, wheel encoders firing at 1 kHz, and a safety system that must react within microseconds. All of this data needs to flow between nodes — but the forklift can't afford the 50–100 µs per message that sockets and pipes add. At 1 kHz, that overhead alone eats 5–10% of every control cycle. And when the vision team splits their processing into a separate process for fault isolation, you can't afford to rewrite every communication path.

HORUS topics solve this with **automatic shared-memory IPC**. You call `send()` and `recv()`. Every topic is shared-memory-backed from the moment it's created; HORUS counts how many publishers and subscribers exist (and whether the payload is plain-old-data) and selects one of four lock-free SHM backends. Latency is dominated by **core locality**, not by the backend: when producer and consumer share an executor thread the data stays L1-hot (~12–19 ns one-way); across threads or processes it's ~220 ns one-way — cache-coherence physics that no backend choice can beat. Because every topic is already SHM-backed, a consumer in another process can attach later with no migration. Your code never changes.

For a gentler introduction, start with [Topics: How Nodes Talk](/concepts/topics-beginner).

## Automatic Backend Selection

HORUS doesn't expose one rigid communication backend — it has four shared-memory backends, each matched to a messaging pattern. Every topic is shared-memory-backed from the moment it's created; the system picks the backend automatically based on two factors:

1. **How many** publishers and subscribers exist?
2. **What payload** — a plain-old-data (POD) type, or one that needs serialization?

Note that these factors select the *pattern*, not the *speed*. Latency is set by **core locality** (see below): a producer and consumer on the same executor thread run ~12–19 ns one-way; anything cross-thread or cross-process is ~220 ns one-way, regardless of which backend is in play.

### Backend Reference

All four backends are shared-memory-backed. They differ in the messaging *pattern* they serve, not in their latency tier:

| Backend | Topology | Payload | Implementation |
|---------|----------|---------|----------------|
| `SpscShm` | 1 publisher : 1 subscriber | any | Lock-free SHM ring, Release/Acquire ordering |
| `MpscShm` | N publishers : 1 subscriber | any | SHM ring + Lamport sequence numbers on head |
| `PodShm` | 1 publisher : N subscribers | POD (plain-old-data) | Memory-mapped broadcast, direct read |
| `FanoutShm` | N:M / non-POD broadcast | any (incl. serialized) | Per-pair SHM SPSC matrix |

### Latency Is Core Locality

Which backend you land on does **not** set your latency — where the producer and consumer run does. The cliff is the CPU cache boundary, not intra-process-vs-shared-memory:

| Route | One-way latency |
|-------|-----------------|
| Same executor thread, self-loop (1 handle, `Both` fast path) | ~12 ns (~24 ns per send+recv) |
| Same executor thread, real pub + sub (2 handles) | ~19 ns (~39 ns per send+recv) |
| Cross-thread **or** cross-process | ~220 ns |

When producer and consumer share a core the payload stays L1-hot (~12–19 ns). The moment they sit on different cores — whether that's two threads or two processes — you pay ~220 ns of cache-coherence traffic, and no backend or layout choice moves that number. An in-process heap ring would *not* beat SHM here. The fastest realistic route is to co-locate a producer and consumer on one executor thread.

<Callout type="info">
**Latencies above are for small messages (~16 bytes).** Larger messages scale linearly with size. A 304-byte IMU message adds ~940 ns cross-process. A 1.5 KB LaserScan adds ~2.2 µs. Pool-backed types (Image, PointCloud) transfer only a small descriptor (~168–280 bytes) regardless of actual data size.
</Callout>

### Joining and Fan-out Changes

Because every topic is shared-memory-backed from creation, a process **split needs no migration at all**: a consumer in another process simply attaches to the existing shared memory — no rewiring, no dropped messages. This is exactly why there is no separate "intra-process" path to migrate away from.

When the fan-out itself changes — a second subscriber joins a 1:1 topic, so the pattern shifts from `SpscShm` toward a broadcast backend (`PodShm` / `FanoutShm`) — HORUS re-selects the matching backend transparently. You never need to configure or trigger this; it happens automatically on the next `send()` or `recv()` after the change is detected.

## Communication Patterns

### One-to-One (SpscShm — ~19 ns same-thread, ~220 ns cross-thread/process)

The simplest pattern: one publisher, one subscriber. Auto-selects `SpscShm` (single-producer, single-consumer) — the leanest backend. Co-locate both nodes on one executor thread and it runs L1-hot (~19 ns one-way); split them across cores or processes and it's ~220 ns either way.

<LanguageTabs>
  <LangTab language="Rust">
    ```rust
// simplified
    use horus::prelude::*;

    // Publisher
    struct Sensor { data_pub: Topic<f32> }
    impl Node for Sensor {
        fn name(&self) -> &str { "Sensor" }
        fn tick(&mut self) { self.data_pub.send(42.0); }
    }

    // Subscriber
    struct Display { data_sub: Topic<f32> }
    impl Node for Display {
        fn name(&self) -> &str { "Display" }
        fn tick(&mut self) {
            if let Some(v) = self.data_sub.recv() { println!("{}", v); }
        }
    }
    ```
  </LangTab>
  <LangTab language="Python">
    ```python
    import horus

    # Publisher
    def sensor_tick(node):
        node.send("sensor.data", 42.0)

    sensor = horus.Node("Sensor", tick=sensor_tick, pubs=["sensor.data"])

    # Subscriber
    def display_tick(node):
        val = node.recv("sensor.data")
        if val is not None:
            print(val)

    display = horus.Node("Display", tick=display_tick, subs=["sensor.data"])

    horus.run(sensor, display)
    ```
  </LangTab>
</LanguageTabs>

### One-to-Many / Broadcast (PodShm or FanoutShm — ~19 ns same-thread, ~220 ns cross-thread/process)

One publisher, multiple subscribers. All subscribers independently receive every message. Auto-selects `PodShm` for plain-old-data payloads (memory-mapped broadcast) or `FanoutShm` for types that need serialization.

<LanguageTabs>
  <LangTab language="Rust">
    ```rust
// simplified
    // One publisher
    struct Broadcaster { alert_pub: Topic<String> }

    // Three independent subscribers — all receive the same data
    struct Logger { alert_sub: Topic<String> }
    struct Dashboard { alert_sub: Topic<String> }
    struct Recorder { alert_sub: Topic<String> }
    ```
  </LangTab>
  <LangTab language="Python">
    ```python
    # One publisher
    broadcaster = horus.Node("Broadcaster", tick=broadcast_tick, pubs=["alert"])

    # Three independent subscribers — all receive the same data
    logger    = horus.Node("Logger",    tick=log_tick,    subs=["alert"])
    dashboard = horus.Node("Dashboard", tick=dash_tick,   subs=["alert"])
    recorder  = horus.Node("Recorder",  tick=record_tick, subs=["alert"])
    ```
  </LangTab>
</LanguageTabs>

This is the standard pattern for sensor data: one camera node publishes, and the vision system, logger, and display all subscribe independently.

### Many-to-One / Aggregation (MpscShm — ~19 ns same-thread, ~220 ns cross-thread/process)

Multiple publishers, one subscriber. Auto-selects `MpscShm` (multiple-producer, single-consumer). Messages are interleaved in arrival order.

<LanguageTabs>
  <LangTab language="Rust">
    ```rust
// simplified
    // Multiple sensors publishing to the same topic
    struct TempSensor1 { pub_temp: Topic<f32> }
    struct TempSensor2 { pub_temp: Topic<f32> }

    // Single aggregator drains all readings
    struct Aggregator { sub_temp: Topic<f32> }

    impl Node for Aggregator {
        fn name(&self) -> &str { "Aggregator" }
        fn tick(&mut self) {
            // Drain all readings — may come from either sensor
            while let Some(reading) = self.sub_temp.recv() {
                self.process(reading);
            }
        }
    }
    ```
  </LangTab>
  <LangTab language="Python">
    ```python
    # Multiple sensors publishing to the same topic
    temp1 = horus.Node("TempSensor1", tick=temp1_tick, pubs=["temperature"])
    temp2 = horus.Node("TempSensor2", tick=temp2_tick, pubs=["temperature"])

    # Single aggregator drains all readings
    def aggregator_tick(node):
        while node.has_msg("temperature"):
            reading = node.recv("temperature")
            process(reading)

    aggregator = horus.Node("Aggregator", tick=aggregator_tick, subs=["temperature"])
    ```
  </LangTab>
</LanguageTabs>

### Many-to-Many (FanoutShm — ~19 ns same-thread, ~220 ns cross-thread/process)

Multiple publishers and subscribers (or any non-POD broadcast). Auto-selects `FanoutShm`, which wires a per-pair SHM SPSC matrix — the most general path. The per-hop latency still follows the core-locality ladder above, but every added publisher/subscriber pair is extra work, so prefer a narrower pattern when you don't genuinely need N:M.

## Topic Naming

### Use Dots, Not Slashes

HORUS uses **dots (`.`)** for topic name hierarchy:

<LanguageTabs>
  <LangTab language="Rust">
    ```rust
// simplified
    // CORRECT
    Topic::<f32>::new("sensor.temperature")?;
    Topic::<CmdVel>::new("robot.motor.cmd_vel")?;
    Topic::<LaserScan>::new("lidar.front.scan")?;

    // WRONG — fails on macOS
    Topic::<f32>::new("sensor/temperature")?;
    ```
  </LangTab>
  <LangTab language="Python">
    ```python
    # CORRECT
    pubs=["sensor.temperature"]
    pubs=["robot.motor.cmd_vel"]
    subs=["lidar.front.scan"]

    # WRONG — fails on macOS
    pubs=["sensor/temperature"]
    ```
  </LangTab>
</LanguageTabs>

<Callout type="warning">
Slashes cause `shm_open` (the POSIX shared-memory system call) to interpret the name as a file path on macOS, creating nested directories instead of a flat shared-memory region. Dots work identically on Linux and macOS.

| Framework | Separator | Example |
|-----------|-----------|---------|
| ROS / ROS2 | `/` | `/sensor/lidar` |
| HORUS | `.` | `sensor.lidar` |
</Callout>

### Naming Conventions

| Pattern | Example | Use for |
|---------|---------|---------|
| `subsystem.data` | `sensor.temperature` | Most topics |
| `subsystem.device.data` | `camera.front.rgb` | Multi-device systems |
| `robot_id.subsystem.data` | `robot1.motor.cmd_vel` | Multi-robot fleets |

**Avoid**: names starting with `_` (reserved for internal use), names containing special characters (`!@#$%^&*()`), and names containing `/`.

### Type-Safe Topic Descriptors

The `topics!` macro defines compile-time topic descriptors that prevent name typos and type mismatches:

<LanguageTabs>
  <LangTab language="Rust">
    ```rust
// simplified
    use horus::prelude::*;

    topics! {
        pub CMD_VEL: CmdVel = "cmd_vel",
        pub SENSOR_DATA: f32 = "sensor.data",
        pub MOTOR_STATUS: MotorStatus = "motor.status",
    }

    // Usage — type is enforced at compile time
    let pub_topic = Topic::<CmdVel>::new(CMD_VEL.name())?;
    let sub_topic = Topic::<CmdVel>::new(CMD_VEL.name())?;
    ```
  </LangTab>
  <LangTab language="Python">
    ```python
    from horus import CmdVel, MotorStatus

    # Typed topic descriptors — type checked at publish/subscribe
    motor = horus.Node(
        "Motor",
        tick=motor_tick,
        pubs=[CmdVel],                         # Type-safe publisher
        subs={"motor.status": MotorStatus},    # Type-safe subscriber
    )
    ```
  </LangTab>
</LanguageTabs>

This catches topic name typos and type mismatches at compile time instead of runtime.

## Message Types

### What Types Work?

Any type that implements `Clone + Send + Sync + Serialize + Deserialize + 'static` works with topics. In practice, this means almost everything:

<LanguageTabs>
  <LangTab language="Rust">
    ```rust
// simplified
    use serde::{Serialize, Deserialize};

    // Primitive types — work out of the box
    let topic: Topic<f32> = Topic::new("float")?;
    let topic: Topic<bool> = Topic::new("flag")?;

    // Custom structs — add standard derives
    #[derive(Clone, Serialize, Deserialize)]
    struct MyMessage {
        x: f32,
        y: f32,
        label: String,
    }
    let topic: Topic<MyMessage> = Topic::new("custom")?;
    ```
  </LangTab>
  <LangTab language="Python">
    ```python
    # Primitive types — work out of the box
    node.send("float", 42.0)
    node.send("flag", True)

    # Custom dicts — sent as-is
    node.send("custom", {"x": 1.0, "y": 2.0, "label": "target"})

    # Dataclasses work too
    from dataclasses import dataclass

    @dataclass
    class MyMessage:
        x: float
        y: float
        label: str

    node.send("custom", MyMessage(x=1.0, y=2.0, label="target"))
    ```
  </LangTab>
</LanguageTabs>

### The TopicMessage Trait

Under the hood, all types go through the `TopicMessage` trait, which defines a **wire format** for transmission:

<LanguageTabs>
  <LangTab language="Rust">
    ```rust
// simplified
    pub trait TopicMessage: Sized + Send + 'static {
        type Wire: Clone + Send + Sync + Serialize + DeserializeOwned + 'static;
        fn to_wire(&self, pool: &Option<Arc<TensorPool>>) -> Self::Wire;
        fn from_wire(wire: Self::Wire, pool: &Option<Arc<TensorPool>>) -> Self;
        fn needs_pool() -> bool;
    }
    ```
  </LangTab>
  <LangTab language="Python">
    ```python
    # Python handles wire format automatically — no manual trait implementation needed.
    # All Python-serializable types (dicts, dataclasses, built-in messages) work
    # out of the box via node.send() and node.recv().
    ```
  </LangTab>
</LanguageTabs>

For most types, the blanket implementation makes `Wire = T` — a direct pass-through with zero overhead. Pool-backed types (Image, PointCloud, DepthImage, Tensor) use a small descriptor as the wire format and transfer the actual data through shared memory pools.

You never need to implement this trait manually — the blanket impl covers all standard types.

### Pool-Backed Types (Zero-Copy for Large Data)

For large data types, copying through the ring buffer would be too slow. A 1920×1080 RGB image is 6 MB — copying it at 30 FPS would consume 180 MB/s of memory bandwidth just for one topic.

HORUS solves this with **pool-backed types**. The actual data lives in a shared memory pool. The topic transfers only a small descriptor (~168–280 bytes) that points to the pool slot. The receiver reads the pixel data directly from the same memory — zero copies regardless of image size.

| Type | Descriptor size | Actual data | Example size |
|------|----------------|-------------|--------------|
| `Image` | 232 bytes | Pixel buffer in SHM pool | 6 MB (1080p RGB) |
| `PointCloud` | 280 bytes | Point array in SHM pool | 1.2 MB (30K points) |
| `DepthImage` | 232 bytes | Depth buffer in SHM pool | 4 MB (1080p f32) |
| `Tensor` | 168 bytes | Tensor data in SHM pool | Varies |

The API is identical — `send()`, `recv()`, `try_send()` all work the same:

<LanguageTabs>
  <LangTab language="Rust">
    ```rust
// simplified
    use horus::prelude::*;

    let camera = Topic::<Image>::new("camera.rgb")?;

    // Send (moves Image into pool slot, sends descriptor through ring)
    camera.send(image);

    // IMPORTANT: drain every tick — images are large and stale frames waste pool slots
    if let Some(img) = camera.recv() {
        println!("{}x{} image received", img.width(), img.height());
    }
    ```
  </LangTab>
  <LangTab language="Python">
    ```python
    from horus import Image

    camera_node = horus.Node("Camera", tick=cam_tick, pubs=[Image])

    # In the publisher tick
    def cam_tick(node):
        node.send("camera.rgb", image)

    # In the subscriber tick — drain every tick to free pool slots
    def vision_tick(node):
        img = node.recv("camera.rgb")
        if img is not None:
            print(f"{img.width}x{img.height} image received")
    ```
  </LangTab>
</LanguageTabs>

<Callout type="tip">
You don't need to use `with_capacity()` for pool-backed types — they manage their own memory through the pool. `Topic::new()` is the correct constructor for Image, PointCloud, DepthImage, and Tensor.
</Callout>

## Memory and Capacity

### Ring Buffer Model

Each topic is backed by a ring buffer with a fixed number of **slots**. When a publisher calls `send()` and all slots are occupied, a point-to-point (1:1) topic rejects the new message (keeping the queued messages in publish order); a broadcast (multi-subscriber) topic overwrites the oldest.

```
Ring buffer (capacity = 4):
┌───┬───┬───┬───┐
│ 3 │ 4 │ 5 │ _ │  ← slot 0 was overwritten by message 4
└───┴───┴───┴───┘
  ↑           ↑
  read        write
  cursor      cursor
```

There is no single default capacity: `Topic::new()` derives it from the message size as `4096 / size_of::<T>()`, clamps the result to **16–1024 slots**, then rounds up to a power of two. So a 4-byte message gets 1024 slots, a 64-byte message gets 64, and anything from roughly 240 bytes upward bottoms out at the 16-slot minimum. Set the capacity explicitly when you need different buffering:

<LanguageTabs>
  <LangTab language="Rust">
    ```rust
// simplified
    // Default: capacity auto-sized from the message size (16–1024 slots)
    let topic = Topic::<Imu>::new("imu")?;

    // Custom: 16 slots, auto-sized — for high-frequency bursty publishers
    let topic = Topic::<Imu>::with_capacity("imu", 16, None)?;

    // Custom: 8 slots, 4 KB each — for large variable-size messages
    let topic = Topic::<LaserScan>::with_capacity("lidar.scan", 8, Some(4096))?;
    ```
  </LangTab>
  <LangTab language="Python">
    ```python
    from horus import Imu, LaserScan

    # Default: capacity auto-sized from the message size (16–1024 slots)
    imu_node = horus.Node("ImuReader", tick=imu_tick, subs=[Imu])

    # Capacity is configured at the Rust level — Python nodes use the
    # default ring buffer size. For custom capacity, configure in horus.toml.
    ```
  </LangTab>
</LanguageTabs>

<Callout type="info">
Capacity must be a power of 2 (4, 8, 16, 32, ...). This allows the ring buffer to use bitwise AND instead of modulo for index wrapping — a micro-optimization that matters at nanosecond latencies.
</Callout>

### Memory Usage

| Message Type | Size | Auto Capacity | Approximate Memory |
|-------------|------|---------------|-------------------|
| `f32` | 4 B | 1024 slots | ~73 KB |
| `CmdVel` | 16 B | 256 slots | ~19 KB |
| `Imu` | ~300 B | 16 slots | ~5 KB |
| `LaserScan` | ~1.5 KB | 16 slots | ~25 KB |

Small POD messages occupy a 64-byte slot each (the sequence number sits on the same cache line as the data), so tiny types cost more per slot than their size suggests. For most robotics applications, total topic memory is well under 1 MB.

### Cleaning Up Shared Memory

Shared memory files persist after processes exit — by design, so new processes can join existing topics. Clean up between sessions:

```bash
horus clean --shm            # Clean shared memory
horus clean --shm --dry-run  # Preview what would be cleaned
horus clean --all            # Clean everything (SHM + build cache)
```

HORUS also performs automatic stale-topic cleanup — files with no active process are removed when new topics are created.

## Runtime Debugging

### CLI Tools

```bash
horus topic list              # List all active topics
horus topic echo sensor.data  # Print messages on a topic
horus topic hz sensor.data    # Show publish rate
horus monitor --tui           # Interactive dashboard
```

### TUI Debug Logging

Debug logging is toggled at runtime from the TUI monitor — no code changes or recompilation needed. Select a topic in the Topics tab and press **Enter** to start logging; press **Esc** to stop.

When active, every `send()` and `recv()` records timing and message summaries. When disabled, there is zero overhead — introspection is fully separated from the hot path.

## Design Decisions

**Why four backends instead of just one "shared memory"?**
A single shared-memory implementation that handles every pattern must use the most conservative synchronization — CAS on both head and tail — even for the common case of one publisher and one subscriber, where a simple Release/Acquire ring (`SpscShm`) does the job. The four backends (`SpscShm`, `MpscShm`, `PodShm`, `FanoutShm`) let each messaging pattern use the minimal synchronization it needs, with automatic selection so you never think about it. Note that this is about synchronization overhead, not the latency tier: latency is governed by core locality (~12–19 ns same executor thread, ~220 ns cross-core), and co-locating a producer and consumer on one thread is the real lever.

**Why ring buffers instead of unbounded queues?**
Unbounded queues grow without limit. A slow subscriber on a fast publisher creates a memory leak that eventually crashes the process. Ring buffers have fixed, predictable memory usage. When full, a 1:1 topic rejects new sends (keeping its queued messages in order) and a broadcast topic overwrites the oldest — the publisher never blocks either way. For guaranteed delivery use `send_blocking()`; for freshest-wins on a 1:1 stream, drain with `recv_all()[-1]`.

**Why automatic backend selection instead of manual configuration?**
During development, everything runs in one process. In production, you split across processes for isolation. In simulation, you might run everything on one thread for determinism. If you had to manually configure the backend for every topology, you'd need different configurations for development, testing, and production. Automatic selection means the same code runs optimally everywhere.

**Why SHM-backed from creation?**
A new subscriber joining shouldn't require restarting the publisher, and a process splitting in two shouldn't require code changes. Because every topic is shared-memory-backed the instant it's created (the creator's PID is stamped at init), a consumer in another process just attaches to the existing shared memory — no migration, no coordination. When the fan-out pattern itself changes, HORUS re-selects the matching backend at runtime, without dropping messages.

**Why dots instead of slashes for naming?**
POSIX `shm_open` on macOS interprets slashes as directory separators. A topic named `"sensor/lidar"` creates a file at `/dev/shm/sensor/lidar` instead of `/dev/shm/sensor.lidar`, which fails if the `sensor/` directory doesn't exist. Dots work identically on Linux and macOS. This was a pragmatic cross-platform decision, not a stylistic one.

## Trade-offs

| Gain | Cost |
|------|------|
| **Four optimized backends** — each messaging pattern gets minimal-overhead sync | More complex internal implementation (transparent to users) |
| **Automatic selection** — same code works across all topologies | Cannot force a specific backend (auto-selection is always optimal) |
| **Ring buffer** — bounded memory, never blocks, always has latest data | Slow subscribers lose messages (detectable via `dropped_count()`) |
| **Pool-backed zero-copy** — 6 MB images transfer in nanoseconds | Pool slots are finite; stale `recv()` wastes slots |
| **SHM-backed from creation** — cross-process consumers attach with no migration | Backend re-selects on fan-out change (brief, transparent) |
| **Type safety** — compiler enforces message types | All serializable types need `Clone + Serialize + Deserialize` derives |
