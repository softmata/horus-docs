# Shared Memory

When nodes run in **different processes**, HORUS automatically uses shared memory for communication. You don't need to configure anything — `Topic::new()` detects the topology and switches to shared memory backends transparently.

## When Shared Memory is Used

HORUS auto-selects the communication backend based on where publishers and subscribers are:

| Scenario | Backend | Mechanism |
|----------|---------|-----------|
| Same thread | DirectChannel (~3ns) | Direct function call |
| Same process, different threads | SpscIntra/MpmcIntra (~18-36ns) | Heap-backed ring buffer |
| **Different processes** | **PodShm/SpscShm/MpmcShm (~50-167ns)** | **Shared memory** |

You always use the same API:

```rust
use horus::prelude::*;

// Same API regardless of whether nodes are in the same process or different processes
let topic: Topic<CmdVel> = Topic::new("cmd_vel")?;
topic.send(CmdVel::new(1.0, 0.5));
```

When a second process opens the same topic name, HORUS automatically migrates to a shared memory backend.

## Cross-Process Communication

HORUS uses a **flat namespace** — all processes on the same machine share the same topic space. No configuration needed:

```bash
# Terminal 1: Sensor process
horus run sensor.rs
# → Topic::new("camera.image") creates /dev/shm/horus/topics/horus_camera.image

# Terminal 2: Controller process (different process, same topic!)
horus run controller.rs
# → Topic::new("camera.image") opens /dev/shm/horus/topics/horus_camera.image
```

Both processes automatically communicate through the shared memory file. This is similar to how ROS topics work.

### Topic Isolation

If you need to run multiple independent HORUS applications on the same machine, use topic name prefixes:

```rust
// Robot arm application
Topic::new("arm.cmd_vel")?;

// Mobile robot application
Topic::new("mobile.cmd_vel")?;
```

These create separate shared memory files and don't interfere with each other.

## Storage Locations

HORUS stores shared memory in platform-specific directories:

| Platform | Path | Notes |
|----------|------|-------|
| Linux | `/dev/shm/horus/` | tmpfs (RAM-backed), fastest |
| macOS | `/tmp/horus/` | Uses temp directory |
| Windows | `%TEMP%\horus\` | Uses temp directory |

### Directory Structure

```
/dev/shm/horus/
├── topics/     # Topic message data (one file per topic)
├── nodes/      # Node presence files (JSON, one per active node)
├── network/    # Network status files
├── params/     # Cross-process runtime parameters
└── control/    # Node lifecycle commands (stop, pause, resume)
```

Separate from the main directory:
```
/dev/shm/horus_logs   # Shared memory log buffer for horus monitor
```

### File Naming

Each topic creates a file named `horus_{topic_name}`:

```bash
# Example files in /dev/shm/horus/topics/
horus_cmd_vel
horus_camera.image
horus_sensors.imu.accel
```

## Capacity and Memory Usage

### Auto-Sizing

By default, `Topic::new()` automatically calculates capacity based on the message type size:

```rust
capacity = (4096 / size_of::<T>()).clamp(16, 1024)
```

- Small types like `f32` (4 bytes): 1024 slots
- Medium types like `CmdVel` (16 bytes): 256 slots
- Larger types: Minimum 16 slots

### Custom Capacity

Use `Topic::with_capacity()` for explicit control:

```rust
// Buffer 500 messages of CmdVel
let topic: Topic<CmdVel> = Topic::with_capacity("cmd_vel", 500, None)?;

// First argument: topic name
// Second argument: number of message slots (u32)
// Third argument: optional custom slot size in bytes (None = auto)
```

### Memory Per Topic

Each topic's shared memory file contains: `HEADER (640B) + SEQ_ARRAY (capacity × 8B) + DATA (capacity × slot_size)`.

Small POD types (≤56 bytes) use a co-located 64-byte slot layout. Larger types use DEFAULT_SLOT_SIZE (8 KB).

| Message Type | Auto Capacity | Slot Size | Approximate Memory |
|--------------|---------------|-----------|-------------------|
| `f32` (4 bytes) | 1024 slots | 64 B (co-located) | ~73 KB |
| `CmdVel` (16 bytes) | 256 slots | 64 B (co-located) | ~19 KB |
| `Pose2D` (32 bytes) | 128 slots | 64 B (co-located) | ~10 KB |
| `Twist` (56 bytes) | 73 slots | 64 B (co-located) | ~6 KB |
| `Imu` (~300 bytes) | 16 slots | 8 KB (default) | ~129 KB |

For most robotics applications, memory usage per topic is minimal (under 1 MB).

## Debugging Shared Memory

### View Active Topics

```bash
# Linux
ls -lh /dev/shm/horus/topics/

# macOS
ls -lh /tmp/horus/topics/

# Example output:
# -rw-r--r-- 1 user user 4.1K Feb 16 12:34 horus_cmd_vel
# -rw-r--r-- 1 user user 5.2K Feb 16 12:34 horus_camera.image
```

### Check Available Space

```bash
# Linux
df -h /dev/shm

# macOS
df -h /tmp
```

### Use HORUS Monitor

```bash
# Real-time monitoring of all topics, nodes, and metrics
horus monitor
```

The monitor shows active topics, message rates, latency metrics, and node status.

## Cleanup

Shared memory files persist after processes exit. This is by design — it allows new processes to join existing topics. But after crashes or between development sessions, you may want to clean up:

```bash
# Clean shared memory only (recommended)
horus clean --shm

# Preview what would be cleaned
horus clean --shm --dry-run

# Clean everything (shared memory + build cache)
horus clean --all
```

Manual cleanup:

```bash
# Linux
rm -rf /dev/shm/horus/

# macOS
rm -rf /tmp/horus/
```

```powershell
# Windows
Remove-Item -Recurse -Force "$env:TEMP\horus"
```

## Troubleshooting

### "No space left on device"

Shared memory directory is full:

```bash
# Check usage (Linux)
df -h /dev/shm

# Clean up
horus clean --shm

# Increase size if needed (Linux, requires sudo)
sudo mount -o remount,size=4G /dev/shm
```

### Stale Shared Memory After Crash

If a node crashes, its shared memory files remain:

```bash
horus clean --shm
```

HORUS also performs automatic stale-topic cleanup — files older than 5 minutes with no active process are removed during discovery.

### "Permission denied"

```bash
# Check permissions (Linux)
ls -la /dev/shm/horus/

# Fix if needed
chmod 755 /dev/shm/horus/
```

### Type Mismatch

If a publisher and subscriber use different types for the same topic name, the data will be corrupted. Ensure both sides use the exact same type:

```rust
// Publisher
let pub_topic: Topic<CmdVel> = Topic::new("cmd_vel")?;

// Subscriber (must be the same type!)
let sub_topic: Topic<CmdVel> = Topic::new("cmd_vel")?;
```
