# Zero-Overhead IPC Architecture

HORUS uses a **zero-overhead IPC architecture** that separates introspection from the hot path. This design ensures that `send()` and `recv()` operate at bare-metal latency (~3-167ns) regardless of whether monitoring tools are attached.

## Key Takeaways

After reading this guide, you will understand:
- Why introspection was separated from IPC operations
- How `with_logging()` enables opt-in introspection at topic creation time
- How external tools monitor Topics without affecting performance
- Performance characteristics of each backend

## Architecture: Separated Introspection

HORUS separates introspection from the hot path. Traditional frameworks embed logging and timing in every message operation, adding 170-640ns of overhead even when no one is monitoring. HORUS avoids this entirely:

## API Reference

### Zero-Overhead Operations

#### `send(msg)`

Sends a message with zero introspection overhead. Infallible — uses ring buffer "keep last" semantics.

```rust
use horus::prelude::*;

let topic: Topic<f32> = Topic::new("sensor")?;

// Zero-overhead send - just the IPC operation
topic.send(42.0);
```

**Characteristics:**
- No timing measurement
- No logging or tracing
- No syscalls beyond the atomic operations
- Infallible — ring buffer overwrites oldest message when full
- **Latency: ~3-167ns** depending on backend

#### `recv() -> Option<T>`

Receives a message with zero introspection overhead.

```rust
// Zero-overhead receive - just reads from shared memory
if let Some(value) = topic.recv() {
    process(value);
}
```

**Characteristics:**
- Non-blocking (returns `None` if no message)
- No timing measurement
- No logging
- **Latency: ~3-167ns** depending on backend

### Introspection Mode (Opt-in via `with_logging()`)

Enable logging and metrics at topic creation time using `with_logging()`. Once enabled, the standard `send()` and `recv()` methods automatically record timing and metrics. Requires `T: LogSummary`.

```rust
use horus::prelude::*;

#[derive(Clone, Copy, Serialize, Deserialize, LogSummary)]
struct SensorData {
    temperature: f32,
    pressure: f32,
}

// Configure once — logging is enabled for the lifetime of this topic
let topic: Topic<SensorData> = Topic::new("sensors")?.with_logging();

// send() and recv() now include introspection automatically
topic.send(SensorData { temperature: 25.0, pressure: 101.3 });

if let Some(data) = topic.recv() {
    // Timing and logging recorded automatically
    process(data);
}
```

The `with_logging()` method requires `T: LogSummary`. Use `#[derive(LogSummary)]` for automatic `Debug`-based summaries, or implement the trait manually for custom formatting (useful for large types like images where you want to log only metadata).

**What `with_logging()` adds to `send()`:**
1. Calls `msg.log_summary()` to produce a compact string
2. Records `Instant::now()` before the IPC operation
3. Performs the IPC send
4. Calculates elapsed IPC time
5. Publishes a `LogEntry` (timestamp, node name, tick number, topic, summary, IPC latency)

**What `with_logging()` adds to `recv()`:**
1. Records `Instant::now()` before the IPC operation
2. Performs the IPC receive
3. If a message was received, calls `msg.log_summary()` and publishes a `LogEntry`

**Latency:** +200-500ns overhead per operation

**How it stays zero-overhead when disabled:** The default path uses `unlikely()` branch prediction hints and `#[cold]` / `#[inline(never)]` annotations on the logging path, ensuring the branch predictor treats the non-logging path as the fast path. The overhead when logging is disabled is less than 1 CPU cycle.

## External Introspection

HORUS provides external tools that monitor Topics without affecting publishers:

### `horus monitor`

Launches a monitoring dashboard. Defaults to a web interface; use `-t` for a terminal UI:

```bash
horus monitor          # Web dashboard on localhost:3000
horus monitor -t       # Terminal UI (TUI) mode
horus monitor --port 8080  # Web dashboard on custom port
```

**How it works:**
- Scans `/dev/shm/horus/topics/` directory
- Reads file metadata (size, mtime, accessing PIDs)
- Calculates message rate from timestamps
- **Zero impact on publishers** — reads existing shared memory

### `horus topic echo <name>`

Subscribes to a topic and prints messages:

```bash
horus topic echo sensors
horus topic echo sensors -n 10      # Echo 10 messages then stop
horus topic echo sensors -r 5       # Limit to 5 Hz display rate
```

**How it works:**
- Creates a new subscriber to the topic
- Reads messages like any other node
- Publishers are unaware of the extra subscriber

### `horus topic hz <name>`

Measures message publication rate:

```bash
horus topic hz cmd_vel
horus topic hz cmd_vel -w 20   # Averaging window of 20 samples
# Output: average rate: 100.02 Hz
```

### Additional Topic Commands

```bash
horus topic list              # List all active topics
horus topic list --json       # JSON output
horus topic info <name>       # Detailed info about a topic
horus topic pub <name> <msg>  # Publish a test message
```

## Backend Performance

HORUS auto-detects the optimal backend from 10 modes based on topology (same-thread, same-process, cross-process), participant pattern (1P1C, 1P-MC, MP-1C, MPMC), and type characteristics (POD vs non-POD).

### Intra-Process Backends (Heap-Backed)

| Backend | Latency | Pattern | Use Case |
|---------|---------|---------|----------|
| **DirectChannel** | ~3ns | Same-thread, 1P1C | Internal pipelines |
| **SpscIntra** | ~18ns | Same-process, 1P1C | Fast 1:1 channels |
| **SpmcIntra** | ~24ns | Same-process, 1P-MC | One publisher, many consumers |
| **MpscIntra** | ~26ns | Same-process, MP-1C | Many publishers, one consumer |
| **MpmcIntra** | ~36ns | Same-process, MPMC | General same-process pub/sub |

### Cross-Process Backends (Shared Memory)

| Backend | Latency | Pattern | Use Case |
|---------|---------|---------|----------|
| **PodShm** | ~50ns | Cross-process, POD types | Fastest cross-process for simple types |
| **MpscShm** | ~65ns | Cross-process, MP-1C | Many publishers, one consumer |
| **SpmcShm** | ~70ns | Cross-process, 1P-MC | One publisher, many consumers |
| **SpscShm** | ~85ns | Cross-process, 1P1C | Simple cross-process 1:1 |
| **MpmcShm** | ~167ns | Cross-process, MPMC | General cross-process (default) |

## When to Use Each API

### Use `send()` / `recv()` (Zero-Overhead)

- Production code
- Real-time control loops
- High-frequency sensors (>100 Hz)
- Latency-critical paths
- When external tools provide sufficient monitoring

```rust
// Control loop - zero overhead critical
impl Node for MotorController {
    fn tick(&mut self) {
        if let Some(cmd) = self.cmd_sub.recv() {
            let output = self.compute_control(cmd);
            self.motor_pub.send(output);
        }
    }
}
```

### Use `with_logging()` Topics (Introspection)

- Development and debugging
- Low-frequency topics (\<10 Hz)
- When you need timing data in your node
- System health monitoring topics

```rust
// Health status - introspection useful, low frequency
// The status type must implement LogSummary for with_logging()
let status_pub: Topic<HealthStatus> = Topic::new("health/status")?.with_logging();

// In your node's tick:
let status = self.collect_health();
// Logging happens automatically — only 1 Hz so overhead is negligible
self.status_pub.send(status);
```

### Use External Tools

- Monitoring production systems
- Debugging without code changes
- Measuring actual throughput
- Comparing before/after optimizations

```bash
# Monitor without touching code
horus topic hz cmd_vel
horus topic echo sensors
horus monitor
```

## Design Rationale

### Why Separate Introspection?

1. **Predictable Performance**: Control loops need guaranteed latency
2. **Opt-in Overhead**: Pay only for what you use
3. **External Observability**: Monitor without code changes
4. **Production Ready**: Same code runs in debug and production

### Why Not Use Conditional Compilation?

```rust
// We considered this but rejected it:
#[cfg(feature = "introspection")]
let start = Instant::now();
```

**Problems:**
- Different binaries for debug vs production
- Can't enable introspection on running system
- Feature flags cascade through dependencies

### Why Infallible `send()`?

The `send()` method is infallible — it always succeeds. When the ring buffer is full, the oldest message is overwritten ("keep last" semantics). This matches robotics conventions where the latest sensor reading is always more valuable than an old one:

```rust
// Simple, clean API — no error handling needed
topic.send(data);
```

This provides:
- Zero cognitive overhead — no `.ok()`, `.unwrap()`, or `?` needed
- Predictable behavior — send always succeeds
- "Keep last" semantics — latest data wins
- Matches ROS2's default QoS policy
