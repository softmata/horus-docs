# Communication Patterns Overview

HORUS provides two communication primitives that cover all robotics messaging needs:

| Pattern | Purpose | Example |
|---------|---------|---------|
| **Topic** | Streaming data (pub/sub) | Sensor readings, motor commands, video frames |
| **Action** | Long-running tasks (goal/feedback/result) | Navigation, arm motion, calibration |

Both work locally (shared memory) and across machines (network transport via configuration).

## Topic: Streaming Pub/Sub

`Topic<T>` is the primary communication primitive. It provides lock-free, zero-copy pub/sub with automatic backend selection from 10 optimized paths.

```rust
use horus::prelude::*;

// Create a topic — backend is auto-detected
let pub_topic: Topic<f32> = Topic::new("sensor.temperature")?;
pub_topic.send(25.3);

// Any number of subscribers can listen
let sub_topic: Topic<f32> = Topic::new("sensor.temperature")?;
if let Some(temp) = sub_topic.recv() {
    hlog!(info, "Temperature: {}", temp);
}
```

### Automatic Backend Selection

You never choose a backend — HORUS detects the optimal one automatically based on:
- **Topology**: Same thread, same process, or cross-process
- **Participants**: How many publishers and subscribers
- **Type**: Whether the message type is POD (Plain Old Data)

| Backend | Latency | When Selected |
|---------|---------|---------------|
| **DirectChannel** | ~3ns | Same thread, single publisher and consumer |
| **SpscIntra** | ~18ns | Same process, 1 publisher, 1 consumer |
| **SpmcIntra** | ~24ns | Same process, 1 publisher, many consumers |
| **MpscIntra** | ~26ns | Same process, many publishers, 1 consumer |
| **MpmcIntra** | ~36ns | Same process, many-to-many |
| **PodShm** | ~50ns | Cross-process, POD type |
| **MpscShm** | ~65ns | Cross-process, many publishers, 1 consumer |
| **SpmcShm** | ~70ns | Cross-process, 1 publisher, many consumers |
| **SpscShm** | ~85ns | Cross-process, 1 publisher, 1 consumer |
| **MpmcShm** | ~167ns | Cross-process, many-to-many |

The backend can change at runtime — if a second subscriber joins a 1P1C topic, HORUS automatically migrates from SPSC to SPMC without dropping messages.

### Key Characteristics

- **Infallible send**: `send()` always succeeds. Ring buffer overwrites oldest message when full ("keep last" semantics).
- **Non-blocking recv**: `recv()` returns `Option<T>`. Returns `None` if no message available.
- **Zero introspection overhead**: No timing, logging, or tracing in the default path. Opt-in via `with_logging()`.

For full Topic API details, see [Topic Communication](/concepts/core-concepts-topic).

## Action: Long-Running Tasks

Actions handle tasks that take time to complete and benefit from progress feedback and cancellation. They follow the **Goal / Feedback / Result** pattern.

### Defining an Action

```rust
use horus::prelude::*;

#[derive(Clone, Debug, Serialize, Deserialize, LogSummary)]
pub struct NavigateGoal {
    pub target_x: f64,
    pub target_y: f64,
}

#[derive(Clone, Debug, Serialize, Deserialize, LogSummary)]
pub struct NavigateFeedback {
    pub distance_remaining: f64,
    pub progress_percent: f32,
}

#[derive(Clone, Debug, Serialize, Deserialize, LogSummary)]
pub struct NavigateResult {
    pub success: bool,
    pub final_x: f64,
    pub final_y: f64,
}

pub struct NavigateToGoal;

impl Action for NavigateToGoal {
    type Goal = NavigateGoal;
    type Feedback = NavigateFeedback;
    type Result = NavigateResult;

    fn name() -> &'static str {
        "navigate_to_goal"
    }
}
```

### Action Server

The server receives goals and executes them:

```rust
let server = ActionServerBuilder::<NavigateToGoal>::new()
    .on_goal(|goal| {
        // Accept or reject the goal
        if goal.target_x.abs() < 100.0 {
            GoalResponse::Accept
        } else {
            GoalResponse::Reject("Target out of range".into())
        }
    })
    .on_execute(|handle| {
        // Execute the task, sending feedback along the way
        let goal = handle.goal();
        let initial_distance = compute_distance(goal);

        loop {
            let distance = compute_distance(goal);
            handle.publish_feedback(NavigateFeedback {
                distance_remaining: distance,
                progress_percent: (1.0 - distance / initial_distance) * 100.0,
            });

            if handle.is_cancel_requested() {
                return GoalOutcome::Canceled(NavigateResult {
                    success: false, final_x: 0.0, final_y: 0.0,
                });
            }

            if distance < 0.1 {
                return GoalOutcome::Succeeded(NavigateResult {
                    success: true,
                    final_x: goal.target_x,
                    final_y: goal.target_y,
                });
            }
        }
    })
    .on_cancel(|_goal_id| {
        CancelResponse::Accept
    })
    .build();
```

### Action Client

The client sends goals and tracks progress:

```rust
let client = ActionClientBuilder::<NavigateToGoal>::new()
    .on_feedback(|_goal_id, feedback| {
        hlog!(info, "Progress: {:.1}%", feedback.progress_percent);
    })
    .on_result(|_goal_id, status, result| {
        match status {
            GoalStatus::Succeeded => {
                hlog!(info, "Arrived at ({}, {})", result.final_x, result.final_y);
            }
            GoalStatus::Aborted => hlog!(warn, "Navigation aborted"),
            GoalStatus::Canceled => hlog!(info, "Navigation canceled"),
            GoalStatus::Preempted => hlog!(info, "Navigation preempted"),
            _ => {}
        }
    })
    .build();

// Send a goal
let goal_handle = client.send_goal(NavigateGoal {
    target_x: 5.0,
    target_y: 3.0,
})?;

// Cancel if needed
goal_handle.cancel();
```

### Goal Lifecycle

```
Pending ──> Active ──> Succeeded
               ├────> Aborted    (server error)
               ├────> Canceled   (client request)
               └────> Preempted  (higher-priority goal)
Pending ──> Rejected             (validation failed)
```

### Preemption Policies

Configure how the server handles new goals while one is active:

| Policy | Behavior |
|--------|----------|
| `PreemptionPolicy::PreemptOld` | New goals cancel the active goal (default) |
| `PreemptionPolicy::RejectNew` | New goals are rejected while one is active |
| `PreemptionPolicy::Priority` | Higher-priority goals preempt lower ones |
| `PreemptionPolicy::Queue { max_size }` | Goals are queued FIFO up to a limit |

## Network Communication

By default, Topics and Actions use shared memory for ultra-fast communication between processes on the same machine. HORUS also supports zero-configuration peer discovery via mDNS (requires the `mdns` feature flag), allowing robots on the same local network to discover each other automatically.

For multi-machine details, see [Network Communication](/concepts/network-communication).

## When to Use What

| Scenario | Use | Why |
|----------|-----|-----|
| Sensor data streaming | **Topic** | Continuous data, latest value matters |
| Motor commands | **Topic** | High frequency, low latency |
| Camera frames | **Topic** | Streaming, multiple consumers |
| Navigate to position | **Action** | Long-running, needs progress feedback |
| Pick-and-place | **Action** | Multi-step, cancellable |
| Calibration routine | **Action** | Takes time, reports progress |
| Emergency stop | **Topic** | Must be instantaneous, no handshake |
| Diagnostics broadcast | **Topic** | Many publishers, flexible topology |

**Rule of thumb**: If it's a continuous stream of data, use **Topic**. If it's a task you'd want to start, monitor, and potentially cancel, use **Action**.

## Composing Patterns

A typical robot system combines all patterns:

```rust
struct NavigationSystem {
    // Topics for streaming sensor data
    lidar_sub: Topic<LidarScan>,
    odom_sub: Topic<Odometry>,

    // Topics for publishing commands
    cmd_vel_pub: Topic<Twist>,
    status_pub: Topic<RobotStatus>,

    // Action server for goal-based navigation
    nav_server: ActionServerNode<NavigateToGoal>,
}
```

The navigation action server subscribes to sensor topics internally, computes a path, publishes velocity commands via topics, and reports progress back to the action client — all using the same underlying shared memory infrastructure.
