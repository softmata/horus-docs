# Communication Patterns Overview

HORUS provides `Topic<T>` as the unified communication primitive that automatically selects the optimal backend based on your usage pattern. Understanding the two fundamental patterns helps you design efficient robotics systems.

## Automatic Backend Selection

`Topic::new()` uses **AdaptiveTopic** to auto-detect the optimal backend from 10 paths:

| Backend | Latency | Pattern | Scope |
|---------|---------|---------|-------|
| DirectChannel | ~3ns | 1P:1C | Same thread |
| SpscIntra | ~18ns | 1P:1C | Same process |
| SpmcIntra | ~24ns | 1P:NC | Same process |
| MpscIntra | ~26ns | NP:1C | Same process |
| MpmcIntra | ~36ns | NP:NC | Same process |
| PodShm | ~50ns | POD types | Cross-process |
| MpscShm | ~65ns | NP:1C | Cross-process |
| SpmcShm | ~70ns | 1P:NC | Cross-process |
| SpscShm | ~85ns | 1P:1C | Cross-process |
| MpmcShm | ~167ns | NP:NC | Cross-process |

## Two Core Patterns

### MPMC: Many-to-Many Pub/Sub

**Pattern**: Multiple publishers → Multiple subscribers
**Use Case**: Broadcasting, flexible topologies, logging
**Semantics**: Buffered queue, all messages delivered

```rust
// Auto-detected MPMC - just use Topic::new()
let pub_topic: Topic<SensorData> = Topic::new("sensors")?;
pub_topic.send(data);

// Many subscribers receive the same data
let sub1: Topic<SensorData> = Topic::new("sensors")?;
let sub2: Topic<SensorData> = Topic::new("sensors")?;
let sub3: Topic<SensorData> = Topic::new("sensors")?;
```

### SPSC: Point-to-Point

**Pattern**: One producer → One consumer
**Use Case**: Control loops, critical paths, 1P1C pipelines
**Semantics**: Latest value only (for real-time performance)

```rust
// Explicit SPSC - use producer()/consumer() for guaranteed 1P:1C
let output: Topic<ImuData> = Topic::producer("imu_raw")?;
output.send(data);

// Consumer (exactly one)
let input: Topic<ImuData> = Topic::consumer("imu_raw")?;
if let Some(data) = input.recv() {
    process(data);
}
```

## Decision Matrix

| Criteria | Use MPMC (Topic::new) | Use SPSC (Topic::producer/consumer) |
|----------|----------------------|-------------------------------------|
| **Number of Consumers** | Multiple subscribers | Exactly one consumer |
| **Message Delivery** | All messages buffered | Latest value only |
| **Latency (local)** | ~36-167ns | ~18-85ns |
| **Latency (network)** | &lt;50µs | 5-15µs |
| **Use Case** | Broadcasting, monitoring | Control loops, pipelines |
| **Topology** | Dynamic, flexible | Fixed, point-to-point |
| **Semantics** | Every message matters | Latest value matters |

## Key Differences

### 1. Message Semantics

**MPMC (Buffering)**:
- Messages are queued
- All messages are delivered to all subscribers
- If buffer fills, oldest messages dropped
- Perfect for: Logging, event streams, commands

**SPSC (Latest Value)**:
- Single slot, always overwrites
- Consumer gets latest value only
- Older unread values are lost
- Perfect for: Sensor readings, state updates, control signals

### 2. Performance

**MPMC (Topic::new)**:
- ~36ns (same process) to ~167ns (cross-process)
- &lt;50µs latency (network)
- Slightly slower due to MPMC coordination

**SPSC (Topic::producer/consumer)**:
- ~18ns (same process) to ~85ns (cross-process)
- 5-15µs latency (network)
- Faster due to SPSC optimization (no contention)

### 3. Topology Flexibility

**MPMC (Topic::new)**:
```rust
// Can add/remove subscribers dynamically
let logger: Topic<Event> = Topic::new("events")?;
let monitor: Topic<Event> = Topic::new("events")?;
let analyzer: Topic<Event> = Topic::new("events")?;
// All receive the same events
```

**SPSC (Topic::producer/consumer)**:
```rust
// Fixed 1P1C topology
let producer: Topic<Data> = Topic::producer("data")?;
let consumer: Topic<Data> = Topic::consumer("data")?;
// Exactly one of each - adding another consumer won't work
```

## When to Use Topic

**Broadcasting to multiple nodes**
```rust
// One camera feeds multiple processors
let camera_pub: Topic<Image> = Topic::new("camera")?;
// subscriber 1: face detection
// subscriber 2: object tracking
// subscriber 3: recording/logging
```

**Logging and monitoring**
```rust
// Many nodes publish diagnostics, one logger subscribes
let diag_pub: Topic<DiagMsg> = Topic::new("diagnostics")?;
let logger: Topic<DiagMsg> = Topic::new("diagnostics")?;
```

**Event-driven systems**
```rust
// Events trigger actions in multiple subsystems
let event_pub: Topic<EmergencyStop> = Topic::new("estop")?;
// All motor controllers subscribe and react
```

**Flexible topologies**
- Number of subscribers unknown at compile time
- Nodes can join/leave during runtime
- Pub/sub pattern from ROS/MQTT/DDS

## When to Use SPSC Topic

**Control loops** (high-frequency, latency-critical)
```rust
// IMU → State Estimator → Controller → Motors
// Each stage connected by explicit SPSC (~18-85ns latency)
struct FlightController {
    imu_input: Topic<ImuData>,     // Created with Topic::consumer()
    motor_output: Topic<MotorCommands>,  // Created with Topic::producer()
}
```

**Point-to-point pipelines**
```rust
// Sensor → Filter → Processor (explicit SPSC for determinism)
let raw_output: Topic<RawData> = Topic::producer("raw")?;
let raw_input: Topic<RawData> = Topic::consumer("raw")?;

let filtered_output: Topic<FilteredData> = Topic::producer("filtered")?;
```

**Latest-value semantics**
```rust
// Always want the newest sensor reading
let lidar: Topic<LidarScan> = Topic::new("lidar")?;
// Old scans are irrelevant - only latest matters
```

**Deterministic real-time systems**
- Fixed topology known at compile time
- Predictable latency critical
- Hard real-time requirements

## Hybrid Patterns

You can combine both patterns in the same system:

```rust
struct RobotSystem {
    // SPSC for critical control loop (~18-85ns)
    imu_input: Topic<ImuData>,       // Topic::consumer()
    motor_output: Topic<MotorCommands>,  // Topic::producer()

    // MPMC for broadcasting and monitoring (~36-167ns)
    status_topic: Topic<RobotStatus>,    // Topic::new()
    diagnostics_topic: Topic<DiagMsg>,   // Topic::new()
    camera_topic: Topic<Image>,          // Topic::new()
}
```

**Design principle**: Use explicit SPSC for the critical path, auto-detected MPMC for everything else.

## Common Patterns

### 1. Sensor Fusion

```rust
// Multiple sensors → One fusion node (Topic MPMC)
let imu_pub: Topic<ImuData> = Topic::new("sensors.imu")?;
let gps_pub: Topic<GpsData> = Topic::new("sensors.gps")?;
let lidar_pub: Topic<LidarScan> = Topic::new("sensors.lidar")?;

// Fusion node subscribes to all
struct FusionNode {
    imu_sub: Topic<ImuData>,
    gps_sub: Topic<GpsData>,
    lidar_sub: Topic<LidarScan>,

    // Fused output via Topic (high performance)
    state_output: Topic<StateEstimate>,
}
```

### 2. Command Distribution

```rust
// One joystick → Multiple motors (MPMC)
let joystick_pub: Topic<JoystickCmd> = Topic::new("joystick")?;

// Each motor controller subscribes
struct MotorController {
    cmd_sub: Topic<JoystickCmd>,      // Topic::new() for MPMC subscription
    motor_output: Topic<MotorPWM>,    // Topic::producer() for SPSC to motor
}
```

### 3. Pipeline Processing

```rust
// Sequential processing (explicit SPSC for determinism)
let raw_out: Topic<RawImage> = Topic::producer("raw")?;
let raw_in: Topic<RawImage> = Topic::consumer("raw")?;

let filtered_out: Topic<FilteredImage> = Topic::producer("filtered")?;
let filtered_in: Topic<FilteredImage> = Topic::consumer("filtered")?;

// raw → filter → detector → tracker
// Each stage: producer output → process → consumer input
```

## Transport Independence

**Important**: Topic supports **local** and **network** transports!

```rust
// Local shared memory (default) - auto-selects optimal backend
let topic: Topic<Data> = Topic::new("topic")?;           // ~36-167ns (MPMC)
let spsc: Topic<Data> = Topic::producer("topic")?;       // ~18-85ns (SPSC)

// Network (just add host to endpoint)
let net_topic: Topic<Data> = Topic::new("topic@192.168.1.5")?;      // &lt;50µs
let net_spsc: Topic<Data> = Topic::producer("topic@192.168.1.5")?;  // 5-15µs
```

The pattern (MPMC vs SPSC) is independent of the transport (local vs network).

See [Communication Transport](/concepts/communication-transport) for details on local vs network.

## Summary

**MPMC (Topic::new)**:
- Many publishers, many subscribers
- All messages buffered and delivered
- Flexible, dynamic topologies
- ~36-167ns local, &lt;50µs network
- Use for: Broadcasting, monitoring, events

**SPSC (Topic::producer/consumer)**:
- One producer, one consumer
- Latest value only (overwrites)
- Fixed, point-to-point topology
- ~18-85ns local, 5-15µs network
- Use for: Control loops, critical paths, pipelines

Choose based on your **communication pattern**, not transport mechanism!
