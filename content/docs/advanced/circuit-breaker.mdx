# Circuit Breaker

The circuit breaker pattern prevents cascading failures by temporarily disabling failing nodes. When a node fails repeatedly, the circuit "opens" to stop calling it, giving it time to recover.

## Overview

Circuit breakers protect against:
- Cascading failures from one failing node
- Resource exhaustion from repeated retry attempts
- System-wide slowdowns from blocked calls

The Scheduler manages circuit breakers automatically — you enable them via a preset and the scheduler handles state transitions, timeouts, and recovery.

## States

| State | Description | Behavior |
|-------|-------------|----------|
| **Closed** | Normal operation | All requests allowed |
| **Open** | Too many failures | Node temporarily disabled |
| **Half-Open** | Testing recovery | Limited requests allowed |

## How It Works

### Closed → Open

When a node's failures reach the threshold, the circuit opens and the node is temporarily disabled:

```
Node fails repeatedly:
  failure_count = 1 → Closed (keep trying)
  failure_count = 2 → Closed (keep trying)
  failure_count = 3 → Open (stop calling node)
```

### Open → Half-Open

After the timeout elapses, the scheduler allows a single trial execution:

```
Circuit open → wait timeout → Half-Open (try one call)
```

### Half-Open → Closed

If the trial succeeds enough times, the circuit closes and the node resumes normal operation:

```
Half-Open:
  success_count = 1 → Half-Open (keep testing)
  success_count = 2 → Half-Open (keep testing)
  success_count = 3 → Closed (fully recovered)
```

## Enabling Circuit Breakers

Use a Scheduler preset that includes circuit breakers:

```rust
use horus::prelude::*;

// All of these enable circuit breakers:
let scheduler = Scheduler::new();              // 5 failures, 5s timeout
let scheduler = Scheduler::deploy();           // 5 failures, 5s timeout
let scheduler = Scheduler::high_performance(); // 3 failures, 100ms timeout
let scheduler = Scheduler::hard_realtime();    // 3 failures, default timeout
```

## Per-Node Failure Policies

Configure different failure handling per node using the node builder:

```rust,ignore
use horus::prelude::*;

let mut scheduler = Scheduler::deploy();

// Critical node: stop immediately on failure
scheduler.add(motor_controller)
    .order(0)
    .failure_policy(FailurePolicy::Fatal)
    .done();

// Sensor node: restart up to 5 times with 100ms delay
scheduler.add(sensor_reader)
    .order(1)
    .failure_policy(FailurePolicy::Restart { max_restarts: 5, delay_ms: 100 })
    .done();

// Logging node: ignore failures entirely
scheduler.add(data_logger)
    .order(5)
    .failure_policy(FailurePolicy::Ignore)
    .done();
```

**Failure policies:**

| Policy | Behavior |
|--------|----------|
| `FailurePolicy::Fatal` | Stop the scheduler immediately |
| `FailurePolicy::Restart { max_restarts, delay_ms }` | Restart the node up to N times |
| `FailurePolicy::Ignore` | Log the failure, continue running |

When circuit breakers are enabled, nodes use their tier's default failure policy unless overridden.

## Monitoring

Circuit breaker state changes are automatically recorded in the [BlackBox](/advanced/blackbox) flight recorder. After a failure, inspect the blackbox to see state transitions:

```rust,ignore
if let Some(bb) = scheduler.blackbox() {
    for record in &bb.anomalies() {
        println!("[tick {}] {:?}", record.tick, record.event);
    }
}
```

## Best Practices

1. **Use presets**: `Scheduler::deploy()` or `Scheduler::high_performance()` enable circuit breakers with sensible defaults.

2. **Set failure policies per node**: Critical nodes should use `FailurePolicy::Fatal`, non-critical nodes can use `Restart` or `Ignore`.

3. **Test failure scenarios**: Verify your system behaves correctly when nodes are temporarily disabled by the circuit breaker.
