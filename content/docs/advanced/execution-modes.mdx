# Execution Modes

<Callout type="info" title="Quick Answer: Which Mode Should I Use?">

**Use the default.** `Scheduler::new()` gives you predictable, priority-ordered execution that works for most robots.

| Your Situation | Recommended Setup |
|----------------|------------------|
| Learning HORUS | `Scheduler::new()` with defaults |
| Prototyping | `Scheduler::new()` |
| Need maximum speed | `Scheduler::new()` with `.compute()` execution class on heavy nodes |
| Safety-critical (medical, aerospace) | `Scheduler::new().require_rt().tick_rate(1000.0.hz())` with `.budget()` |

**Don't overthink this.** Start with `Scheduler::new()` and configure per-node execution classes as needed.

</Callout>

HORUS supports two execution modes to optimize for different robotics scenarios. You configure the scheduler through `Scheduler::new()` with composable builder methods like `.monitoring(true)`, `.require_rt()`, `.with_blackbox(n)` and per-node execution classes (`.compute()`, `.on(topic)`, `.async_io()`) — the scheduler handles the rest. RT is auto-detected when you set `.budget()`, `.deadline()`, or `.rate(Frequency)` on a node.

## Sequential Mode

**The predictable choice for safety-critical systems.**

Sequential mode is the default. Nodes execute one-by-one in priority order, producing the same execution order every tick.

### How It Works

- Nodes execute one-by-one in priority order
- Same execution order every tick
- Predictable, repeatable behavior

### Characteristics

| Metric | Value |
|--------|-------|
| Latency | ~100-500ns per node |
| Predictable | **Yes** — same order every tick |
| Multi-core | No (single thread) |
| Best For | Safety-critical, certification |

### When to Use

- Medical/surgical robots requiring certification
- Systems needing reproducible behavior
- Debugging complex timing issues
- Formal verification scenarios

Sequential mode is the default when nodes are added with distinct order values. Use `Scheduler::new()` and set budgets (e.g., `.budget()`) on nodes that need real-time constraints — RT is auto-detected.

```rust,ignore
use horus::prelude::*;

// Safety-critical robot controller — 1 kHz tick, RT auto-detected from budget
let mut scheduler = Scheduler::new()
    .require_rt()
    .with_blackbox(64)
    .with_profiling()
    .tick_rate(1000.0.hz());
scheduler.add(safety_monitor).order(0).budget(100.us()).build()?;
scheduler.add(controller).order(1).budget(200.us()).build()?;
scheduler.run()?;
```

## Parallel Mode

**Multi-core execution for maximum throughput.**

Parallel mode schedules independent nodes on different CPU cores, executing them concurrently while still respecting priority ordering.

### How It Works

- Schedules independent nodes on different cores
- Respects priority ordering
- Uses thread pool for concurrent execution

### Characteristics

| Metric | Value |
|--------|-------|
| Latency | Variable (depends on workload) |
| Predictable | Ordering within same priority level varies |
| Multi-core | **Yes** |
| Best For | Multi-sensor fusion, compute-heavy pipelines |

### When to Use

- Multi-sensor robots
- Compute-heavy pipelines
- Systems with many independent nodes
- When you have multiple CPU cores available

The scheduler uses parallel mode when multiple nodes share the same order value and are configured with execution classes like `.compute()`. Nodes at the same order level can run concurrently across cores:

```rust,ignore
use horus::prelude::*;

let mut scheduler = Scheduler::new();

// These sensor nodes can run in parallel (same order number)
scheduler.add(lidar_node).order(0).build()?;
scheduler.add(camera_node).order(0).build()?;
scheduler.add(imu_node).order(0).build()?;

// Fusion runs after all sensors (higher order number = runs later)
scheduler.add(fusion_node).order(1).build()?;
scheduler.run()?;
```

## Mode Comparison

| Feature | Sequential | Parallel |
|---------|------------|----------|
| Predictable Order | **Yes** | Per-priority level |
| Multi-core | No | **Yes** |
| Best Latency | 87-313ns | Variable |
| Certification Ready | **Yes** | No |

## Examples

### Safety-Critical System

```rust,ignore
use horus::prelude::*;

// Surgical robot — predictable sequential, 1 kHz tick with RT auto-detected from budget
let mut scheduler = Scheduler::new()
    .require_rt()
    .with_blackbox(64)
    .with_profiling()
    .tick_rate(1000.0.hz());
scheduler.add(safety_monitor).order(0).budget(100.us()).build()?;
scheduler.add(force_feedback).order(1).budget(200.us()).build()?;
scheduler.add(motion_controller).order(1).budget(200.us()).build()?;
scheduler.run()?;
```

### Racing Robot

```rust,ignore
use horus::prelude::*;

// Competition robot — maximum speed, compute-heavy nodes run in parallel
let mut scheduler = Scheduler::new();
scheduler.add(imu_reader).order(0).compute().build()?;
scheduler.add(motor_controller).order(0).compute().build()?;
scheduler.run()?;
```

### Multi-Sensor Robot

```rust,ignore
use horus::prelude::*;

// Research robot with many sensors — parallel sensor processing
let mut scheduler = Scheduler::new();

// These run in parallel (same order number)
scheduler.add(lidar).order(0).build()?;
scheduler.add(camera).order(0).build()?;
scheduler.add(radar).order(0).build()?;
scheduler.add(imu).order(0).build()?;
// Fusion runs after all sensors (higher order number = runs later)
scheduler.add(fusion).order(1).build()?;
scheduler.run()?;
```
