# Scheduling Intelligence

<Callout type="info" title="Do I Need This?">

**No, tiers work automatically.** When you enable learning with `scheduler.enable_learning()` or use `Scheduler::high_performance()`, HORUS automatically:
1. Profiles your nodes for ~100 ticks
2. Classifies them by behavior (fast, slow, I/O-heavy, etc.)
3. Optimizes execution for each type

**Most users never need to think about tiers.** This page explains how to optionally annotate nodes and what happens under the hood.

**When this page IS useful:**
- You want deterministic startup (skip learning phase)
- Forcing a specific tier for a node
- Understanding why nodes execute differently

</Callout>

## Why Tiers Exist

Different nodes have different needs:

| Node Type | Example | Problem | Solution (Tier) |
|-----------|---------|---------|-----------------|
| Fast math | PID controller | Overhead from function calls | **Jit**: JIT compile to native code |
| Blocking I/O | Camera reader | Blocks the scheduler | **AsyncIO**: Run in async runtime |
| Slow/unreliable | Flaky sensor | Can crash or hang | **Isolated**: Process isolation |
| Normal | Most nodes | None | **Fast**: Inline execution |

Without tiers, a slow camera node would block your fast control loop. Tiers let different nodes run in appropriate ways.

## Node Tier Annotation

Use `NodeTier` to explicitly declare a node's execution characteristics:

```rust
use horus::prelude::*;

let mut scheduler = Scheduler::new();

// Annotate nodes with their tier
scheduler.add(pid_node).order(0).tier(NodeTier::Jit).done();
scheduler.add(sensor_node).order(1).tier(NodeTier::Fast).done();
scheduler.add(camera_node).order(2).tier(NodeTier::AsyncIO).done();
scheduler.add(logger_node).order(5).tier(NodeTier::Background).done();

scheduler.run();
```

### Available Tiers

| Tier | Use For | Latency | Execution |
|------|---------|---------|-----------|
| `NodeTier::Jit` | Ultra-fast math (<1µs) | 20-50ns | JIT compiled |
| `NodeTier::Fast` | Sensors, filters (<10µs) | 50-100ns | Inline |
| `NodeTier::Normal` | Algorithms (<100µs) | ~1µs | Standard |
| `NodeTier::AsyncIO` | Network, file I/O | 10-100µs | Async executor |
| `NodeTier::Background` | Logging, diagnostics | 1-100ms | Thread pool |
| `NodeTier::Isolated` | Unreliable/untrusted | 1-10ms | Process isolation |
| `NodeTier::Auto` | Let system decide | Varies | Based on profile |

### Tier Descriptions

```rust
// Get human-readable description
let tier = NodeTier::Jit;
println!("{}", tier.description());
// Output: "JIT compiled (<1μs)"
```

## Automatic Classification

If you don't annotate nodes, HORUS classifies them automatically during a learning phase:

```rust
use horus::prelude::*;

let mut scheduler = Scheduler::new();

// Enable learning (profiles nodes for ~100 ticks)
scheduler.enable_learning();

// Add nodes without explicit tiers
scheduler.add(sensor_node).order(0).done();
scheduler.add(filter_node).order(1).done();

// During the first ~100 ticks, HORUS profiles execution times
// After learning, nodes are automatically assigned optimal tiers
scheduler.run();
```

### Classification Criteria

The scheduler internally classifies nodes based on:

| Characteristic | Detection | Tier Assignment |
|----------------|-----------|-----------------|
| High failure rate (>20%) | Tracks failures | → Isolated |
| Ultra-fast (<5µs) + deterministic | Low variance | → Jit |
| I/O heavy (high variance) | CV >30%, spikes | → AsyncIO |
| Fast (<1ms) | Execution time | → Fast |
| Everything else | Default | → Background |

## Deterministic Mode (Skip Learning)

For production systems that need deterministic startup:

```rust
use horus::prelude::*;

// Option 1: Annotate all nodes explicitly
let mut scheduler = Scheduler::new();
scheduler.add(node1).tier(NodeTier::Jit).done();
scheduler.add(node2).tier(NodeTier::Fast).done();
// No learning phase needed - deterministic startup

// Option 2: Use offline profiles
let mut scheduler = Scheduler::new();
scheduler.load_profile("profiles/robot.json")?;
// Tiers loaded from pre-computed profile
```

### Creating Offline Profiles

Profile your system once in a controlled environment:

```rust
use horus::prelude::*;

// Create offline profiler
let mut profiler = OfflineProfiler::new();

// Profile each node
profiler.profile_node("sensor", || {
    sensor_node.tick();
});

profiler.profile_node("filter", || {
    filter_node.tick();
});

// Save profile for production use
profiler.save("profiles/robot.json")?;
```

### Loading Profiles

```rust
use horus::prelude::*;

// Load pre-computed profile
let profile = ProfileData::load("profiles/robot.json")?;

// Apply to scheduler
let mut scheduler = Scheduler::new();
scheduler.apply_profile(&profile);

// Nodes now use profiled tiers - no learning phase
scheduler.run();
```

## Best Practices

### 1. Start Without Annotations

Let the system classify nodes automatically. Only annotate when needed:

```rust
// Good: Let HORUS decide
scheduler.add(my_node).done();

// Only annotate when you know better than the profiler
scheduler.add(critical_pid).tier(NodeTier::Jit).done();
```

### 2. Use Offline Profiles for Production

```rust
// Development: Enable learning
scheduler.enable_learning();

// Production: Use offline profile for deterministic startup
scheduler.load_profile("production.json")?;
```

### 3. Monitor Classification Results

```rust
// After learning phase completes
if scheduler.is_learning_complete() {
    scheduler.print_tier_summary();
}
```

## How It Works Internally

<Callout type="note" title="Implementation Details">

The following describes internal behavior. You don't need to understand this to use HORUS effectively.

</Callout>

When learning is enabled, HORUS:

1. **Profiles** each node for ~100 ticks using Welford's algorithm for stable statistics
2. **Analyzes** execution characteristics:
   - Mean and standard deviation of execution time
   - Coefficient of variation (determinism)
   - Failure rate
   - I/O patterns (high variance indicates blocking I/O)
3. **Classifies** nodes into internal execution tiers
4. **Optimizes** execution:
   - Ultra-fast nodes → JIT compiled
   - I/O-heavy nodes → Async executor
   - Unreliable nodes → Process isolation
   - Normal nodes → Inline execution
