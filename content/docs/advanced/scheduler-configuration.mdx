# Scheduler Configuration

HORUS uses a single scheduler entry point — `Scheduler::new()` — with a fluent node builder API that gives you full control over execution class, timing, ordering, and failure handling on a per-node basis.

## Creating a Scheduler

Every scheduler starts with `Scheduler::new()`. From there you can optionally set global parameters with builder methods before adding nodes:

```rust
use horus::prelude::*;

fn main() -> Result<()> {
    let mut scheduler = Scheduler::new()
        .tick_hz(1000.0)          // Global tick rate (default: 60 Hz)
        .with_capacity(32)        // Pre-allocate for 32 nodes
        .with_name("arm_control");// Name for logging/profiling

    // ... add nodes ...

    scheduler.run()?;
    Ok(())
}
```

### Builder Methods

| Method | Description | Default |
|--------|-------------|---------|
| `.tick_hz(hz)` | Global scheduler tick rate in Hz | `60.0` |
| `.with_capacity(n)` | Pre-allocate node storage | `16` |
| `.with_name(name)` | Human-readable scheduler name | `"default"` |

## Adding Nodes

Add nodes with `scheduler.add(n)`, then chain configuration calls, and finalize with `.done()`:

```rust
use horus::prelude::*;

fn main() -> Result<()> {
    let mut scheduler = Scheduler::new()
        .tick_hz(1000.0);

    // Real-time motor control — runs first every tick
    scheduler.add(MotorController::new("arm"))
        .order(0)
        .rt()
        .wcet_us(200)
        .deadline_ms(1)
        .done();

    // Sensor node — high priority, custom rate
    scheduler.add(LidarDriver::new("/dev/lidar0"))
        .order(10)
        .rt()
        .rate_hz(500.0)
        .done();

    // Compute-heavy planning — runs on a worker thread
    scheduler.add(PathPlanner::new())
        .order(50)
        .compute()
        .done();

    // Event-driven node — wakes only when the topic has new data
    scheduler.add(CollisionChecker::new())
        .on("lidar/points")
        .deadline_ms(5)
        .done();

    // Async I/O — network or disk, never blocks the real-time loop
    scheduler.add(TelemetryUploader::new())
        .order(200)
        .async_io()
        .rate_hz(10.0)
        .done();

    scheduler.run()?;
    Ok(())
}
```

## Execution Classes

Every node belongs to exactly one execution class. Set it in the builder chain:

| Method | Class | Description |
|--------|-------|-------------|
| `.rt()` | Real-Time | Runs in the scheduler's RT loop. Use for control, safety, and sensors. |
| `.compute()` | Compute | Offloaded to a worker thread pool. Use for planning, SLAM, or ML inference. |
| `.on(topic)` | Event-Driven | Wakes only when the named topic receives new data. |
| `.async_io()` | Async I/O | Runs on an async executor. Use for network, disk, or cloud calls. |

If no execution class is specified, the node defaults to the RT class.

### When to Use Each Class

- **`.rt()`** — Motor controllers, safety monitors, sensor fusion, anything that must run every tick with bounded latency.
- **`.compute()`** — Path planning, point cloud processing, ML inference. These can take longer than a single tick without blocking RT nodes.
- **`.on(topic)`** — Collision detection, event handlers, reactive behaviors. Only runs when there is new data, saving CPU when idle.
- **`.async_io()`** — Telemetry upload, log shipping, cloud API calls. Never blocks any real-time or compute work.

## Per-Node Configuration

### Ordering and Timing

| Method | Description |
|--------|-------------|
| `.order(n)` | Execution priority within a tick (lower = runs first) |
| `.rate_hz(hz)` | Node-specific tick rate, independent of the global rate |
| `.wcet_us(us)` | Worst-Case Execution Time budget in microseconds |
| `.deadline_ms(ms)` | Deadline in milliseconds from tick start |
| `.deadline_us(us)` | Deadline in microseconds from tick start |

### Tier and Failure Policy

| Method | Description |
|--------|-------------|
| `.tier(NodeTier)` | Explicit execution tier (`Critical`, `Standard`, `BestEffort`) |
| `.failure_policy(policy)` | Per-node failure handling (see [Circuit Breaker](/advanced/circuit-breaker)) |
| `.done()` | Finalize and register the node |

### Order Guidelines

- **0-9**: Critical real-time (motor control, safety)
- **10-49**: High priority (sensors, fast control loops)
- **50-99**: Normal priority (processing, planning)
- **100-199**: Low priority (logging, diagnostics)
- **200+**: Background (telemetry, non-essential)

## Global Configuration with Builder Methods

For complex setups, chain builder methods on `Scheduler::new()`:

```rust
use horus::prelude::*;

let mut scheduler = Scheduler::new()
    .tick_hz(1000.0)
    .with_profiling()
    .memory_locked(true)
    .with_blackbox(64)
    .circuit_breaker(true);
```

This is useful when you need to toggle features like memory locking or black-box recording without changing node code.

## OS Priority

Set real-time OS scheduling priority:

```rust
let scheduler = Scheduler::new();
scheduler.set_os_priority(50)?;  // Set SCHED_FIFO priority 1-99
```

Note: Requires root or `CAP_SYS_NICE` capability on Linux.

## Python API

The Python API mirrors the Rust fluent builder:

```python
from horus import Scheduler

# Create scheduler with global settings
scheduler = Scheduler(tick_hz=1000.0, name="arm_control")

# Real-time motor controller
scheduler.add(motor_ctrl).order(0).rt().wcet_us(200).deadline_ms(1).done()

# Sensor with custom rate
scheduler.add(lidar).order(10).rt().rate_hz(500.0).done()

# Compute node
scheduler.add(planner).order(50).compute().done()

# Event-driven node
scheduler.add(collision).on("lidar/points").deadline_ms(5).done()

# Async I/O node
scheduler.add(telemetry).order(200).async_io().rate_hz(10.0).done()

scheduler.run()
```

You can also pass a config dict for global settings:

```python
scheduler = Scheduler(config={
    "tick_hz": 1000.0,
    "enable_profiling": True,
    "memory_lock": True,
    "black_box_size_mb": 64,
})
```

## Node Tiers

Different nodes have different execution time characteristics. Tiers let you declare a node's profile so the scheduler can make informed decisions about failure policies.

| Node Type | Example | Typical Execution | Tier |
|-----------|---------|-------------------|------|
| Fast math | PID controller | &lt;1μs | **UltraFast** |
| Sensors | Camera reader, IMU | &lt;10μs | **Fast** |
| Algorithms | Path planner | &lt;100μs+ | **Normal** |

### Using Tiers

```rust,ignore
use horus::prelude::*;

let mut scheduler = Scheduler::new();

scheduler.add(pid_node).order(0).tier(NodeTier::UltraFast).done();
scheduler.add(sensor_node).order(1).tier(NodeTier::Fast).done();
scheduler.add(planner_node).order(2).tier(NodeTier::Normal).done();

scheduler.run()?;
```

### Tier Reference

| Tier | Use For | Default Failure Policy |
|------|---------|----------------------|
| `NodeTier::UltraFast` | Ultra-fast math (&lt;1μs) | Fatal (stop on failure) |
| `NodeTier::Fast` | Sensors, filters (&lt;10μs) | Fatal |
| `NodeTier::Normal` | Algorithms (&lt;100μs+) | Restart (5 attempts, 100ms delay) |

Most nodes work fine without tier annotations (defaults to `Fast`). Only annotate when you have specific performance needs:

```rust,ignore
// Good: Let HORUS use the default tier
scheduler.add(my_node).done();

// Only annotate when you have specific performance needs
scheduler.add(critical_pid).tier(NodeTier::UltraFast).done();
```

## Execution Modes

HORUS supports sequential and parallel execution. You configure this through `Scheduler::new()` and per-node execution classes.

<Callout type="info" title="Quick Answer">

**Use the default.** `Scheduler::new()` gives you deterministic, predictable execution that works for most robots. Start there and configure per-node execution classes as needed.

</Callout>

### Sequential Mode (Default)

Nodes execute one-by-one in priority order — same execution order every tick. Deterministic and certification-ready.

| Metric | Value |
|--------|-------|
| Latency | ~100-500ns per node |
| Deterministic | **Yes** |
| Multi-core | No (single thread) |
| Best For | Safety-critical, certification |

```rust,ignore
use horus::prelude::*;

// Safety-critical robot controller — 1 kHz tick, RT execution class
let mut scheduler = Scheduler::new().tick_hz(1000.0);
scheduler.add(safety_monitor).rt().order(0).done();
scheduler.add(controller).rt().order(1).done();
scheduler.run()?;
```

### Parallel Mode

Schedules independent nodes on different CPU cores. Nodes at the same `order` level run concurrently:

| Metric | Value |
|--------|-------|
| Latency | Variable (depends on workload) |
| Deterministic | No |
| Multi-core | **Yes** |
| Best For | Multi-sensor fusion, compute-heavy pipelines |

```rust,ignore
use horus::prelude::*;

let mut scheduler = Scheduler::new();

// These sensor nodes run in parallel (same order number)
scheduler.add(lidar_node).order(0).done();
scheduler.add(camera_node).order(0).done();
scheduler.add(imu_node).order(0).done();

// Fusion runs after all sensors (higher order number)
scheduler.add(fusion_node).order(1).done();
scheduler.run()?;
```

### Mode Comparison

| Feature | Sequential | Parallel |
|---------|------------|----------|
| Deterministic | **Yes** | No |
| Multi-core | No | **Yes** |
| Best Latency | 87-313ns | Variable |
| Certification Ready | **Yes** | No |
