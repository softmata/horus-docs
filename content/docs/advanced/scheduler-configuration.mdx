# Scheduler Configuration

HORUS uses a single scheduler entry point — `Scheduler::new()` — with composable builder methods (`.monitoring(true)`, `.require_rt()`, `.with_blackbox(n)`, `.with_profiling()`) and a fluent node builder API that gives you full control over execution class, timing, ordering, and failure handling on a per-node basis.

## Creating a Scheduler

Every scheduler starts with `Scheduler::new()`. From there you can optionally set global parameters with builder methods before adding nodes:

```rust
use horus::prelude::*;

fn main() -> Result<()> {
    let mut scheduler = Scheduler::new()
        .tick_rate(1000.0.hz())          // Global tick rate (default: 60 Hz)
        .with_capacity(32)        // Pre-allocate for 32 nodes
        .with_name("arm_control");// Name for logging/profiling

    // ... add nodes ...

    scheduler.run()?;
    Ok(())
}
```

### Builder Methods

| Method | Description | Default |
|--------|-------------|---------|
| `.tick_rate(hz.hz())` | Global scheduler tick rate in Hz | `60.0` |
| `.with_capacity(n)` | Pre-allocate node storage | `16` |
| `.with_name(name)` | Human-readable scheduler name | `"default"` |
| `.monitoring(true)` | Safety monitor + watchdog + budget enforcement | — |
| `.require_rt()` | Hard real-time — panics without RT capabilities | — |
| `.prefer_rt()` | Request RT features (degrades gracefully) | — |
| `.with_blackbox(n)` | BlackBox flight recorder (n MB) | — |
| `.with_profiling()` | Runtime profiling | — |
| `.deterministic(true)` | Deterministic execution | — |

## Adding Nodes

Add nodes with `scheduler.add(n)`, then chain configuration calls, and finalize with `.build()?` (or its alias `.build()`):

```rust
use horus::prelude::*;

fn main() -> Result<()> {
    let mut scheduler = Scheduler::new()
        .tick_rate(1000.0.hz());

    // Real-time motor control — runs first every tick
    // budget() auto-marks this node as RT
    scheduler.add(MotorController::new("arm"))
        .order(0)
        .budget(200.us())
        .deadline(1.ms())
        .on_miss(Miss::Skip)
        .build()?;

    // Sensor node — high priority, custom rate
    // rate() auto-derives budget and deadline, auto-marks as RT
    scheduler.add(LidarDriver::new("/dev/lidar0"))
        .order(10)
        .rate(500.hz())
        .build()?;

    // Compute-heavy planning — runs on a worker thread
    scheduler.add(PathPlanner::new())
        .order(50)
        .compute()
        .build()?;

    // Event-driven node — wakes only when the topic has new data
    scheduler.add(CollisionChecker::new())
        .on("lidar/points")
        .deadline(5.ms())
        .build()?;

    // Async I/O — network or disk, never blocks the real-time loop
    scheduler.add(TelemetryUploader::new())
        .order(200)
        .async_io()
        .rate(10.0.hz())
        .build()?;

    scheduler.run()?;
    Ok(())
}
```

## Execution Classes

Every node belongs to exactly one execution class. Set it in the builder chain:

| Method | Class | Description |
|--------|-------|-------------|
| `.compute()` | Compute | Offloaded to a worker thread pool. Use for planning, SLAM, or ML inference. |
| `.on(topic)` | Event-Driven | Wakes only when the named topic receives new data. |
| `.async_io()` | Async I/O | Runs on an async executor. Use for network, disk, or cloud calls. |

If no execution class is specified, the node defaults to **BestEffort**. A node is automatically promoted to the **RT** class when you set `.budget()`, `.deadline()`, or `.rate(Frequency)`.

### When to Use Each Class

- **RT (auto-detected)** — Motor controllers, safety monitors, sensor fusion, anything that must run every tick with bounded latency. Triggered by `.budget()`, `.deadline()`, or `.rate(Frequency)`.
- **`.compute()`** — Path planning, point cloud processing, ML inference. These can take longer than a single tick without blocking RT nodes.
- **`.on(topic)`** — Collision detection, event handlers, reactive behaviors. Only runs when there is new data, saving CPU when idle.
- **`.async_io()`** — Telemetry upload, log shipping, cloud API calls. Never blocks any real-time or compute work.

## Per-Node Configuration

### Ordering and Timing

| Method | Description |
|--------|-------------|
| `.order(n)` | Execution priority within a tick (lower = runs first) |
| `.rate(hz.hz())` | Node-specific tick rate, independent of the global rate |
| `.rate(Frequency)` | Rate from `100.hz()` — auto-derives budget and deadline (auto-marks as RT) |
| `.budget(Duration)` | Tick budget, e.g. `200.us()` (auto-marks as RT) |
| `.deadline(Duration)` | Deadline, e.g. `1.ms()` (auto-marks as RT) |
| `.on_miss(Miss)` | What to do on deadline miss (`Miss::Warn`, `Miss::Skip`, `Miss::SafeMode`, `Miss::Stop`) |

### Failure Policy

| Method | Description |
|--------|-------------|
| `.failure_policy(policy)` | Per-node failure handling (see [Fault Tolerance](/advanced/circuit-breaker)) |
| `.build()` / `.build()` | Finalize and register the node (returns `HorusResult`) |

### Order Guidelines

- **0-9**: Critical real-time (motor control, safety)
- **10-49**: High priority (sensors, fast control loops)
- **50-99**: Normal priority (processing, planning)
- **100-199**: Low priority (logging, diagnostics)
- **200+**: Background (telemetry, non-essential)

## Global Configuration with Composable Builders

Instead of toggling individual flags, compose the builder methods you need for each deployment stage:

```rust
use horus::prelude::*;

// Development — lightweight
let mut scheduler = Scheduler::new()
    .tick_rate(1000.0.hz())
    .with_profiling();

// Production — safety + watchdog + budget enforcement
let mut scheduler = Scheduler::new()
    .monitoring(true)
    .tick_rate(1000.0.hz())
    .cores(&[2, 3]);

// Hard real-time — panics without RT capabilities
let mut scheduler = Scheduler::new()
    .require_rt()
    .tick_rate(1000.0.hz());

// Safety-critical — require_rt + blackbox + profiling
let mut scheduler = Scheduler::new()
    .require_rt()
    .with_blackbox(64)
    .with_profiling()
    .tick_rate(1000.0.hz())
    .max_deadline_misses(3);
```

## Python API

The Python API mirrors the Rust fluent builder:

```python
from horus import Scheduler

# Fluent API — configure nodes inline with chained calls
scheduler = Scheduler()
scheduler.node(motor_ctrl).order(0).budget(200).rate(1000.0).build()
scheduler.node(planner).order(5).compute().build()
scheduler.node(telemetry).order(10).async_io().rate(1.0).build()
```

You can also use keyword arguments with `add()`:

```python
scheduler.add(sensor, order=0, rate=100.0)
scheduler.add(controller, order=1, budget=200, on_miss="safe_mode", deadline=5.0)
scheduler.add(logger, order=2, rate=10.0)
scheduler.add(monitor, order=3, failure_policy="skip")
```

Create a scheduler with a `SchedulerConfig`:

```python
from horus import Scheduler, SchedulerConfig

# Create scheduler with config
cfg = SchedulerConfig.with_monitoring()
cfg.tick_rate = 1000.0
scheduler = Scheduler(config=cfg)
```

Composable config for different deployment stages:

```python
from horus import Scheduler, SchedulerConfig

# Development — lightweight
scheduler = Scheduler()

# Production — safety + monitoring
cfg = SchedulerConfig.with_monitoring()
cfg.tick_rate = 1000.0
scheduler = Scheduler(config=cfg)

# With blackbox
cfg = SchedulerConfig.with_monitoring()
cfg.tick_rate = 1000.0
cfg.black_box_enabled = True
cfg.black_box_size_mb = 64
scheduler = Scheduler(config=cfg)
```

## Execution Modes

HORUS supports sequential and parallel execution. You configure this through `Scheduler::new()` and per-node execution classes.

<Callout type="info" title="Quick Answer">

**Use the default.** `Scheduler::new()` gives you predictable, priority-ordered execution that works for most robots. Start there and configure per-node execution classes as needed.

</Callout>

### Sequential Mode (Default)

Nodes execute one-by-one in priority order — same execution order every tick. Predictable and certification-ready.

| Metric | Value |
|--------|-------|
| Latency | ~100-500ns per node |
| Predictable | **Yes** — same order every tick |
| Multi-core | No (single thread) |
| Best For | Safety-critical, certification |

```rust,ignore
use horus::prelude::*;

// Safety-critical robot controller — 1 kHz tick
// budget() auto-marks nodes as RT
let mut scheduler = Scheduler::new().tick_rate(1000.0.hz());
scheduler.add(safety_monitor).order(0).budget(100.us()).build()?;
scheduler.add(controller).order(1).budget(200.us()).build()?;
scheduler.run()?;
```

### Parallel Mode

Schedules independent nodes on different CPU cores. Nodes at the same `order` level run concurrently:

| Metric | Value |
|--------|-------|
| Latency | Variable (depends on workload) |
| Predictable | Ordering within same priority level varies |
| Multi-core | **Yes** |
| Best For | Multi-sensor fusion, compute-heavy pipelines |

```rust,ignore
use horus::prelude::*;

let mut scheduler = Scheduler::new();

// These sensor nodes run in parallel (same order number)
scheduler.add(lidar_node).order(0).build()?;
scheduler.add(camera_node).order(0).build()?;
scheduler.add(imu_node).order(0).build()?;

// Fusion runs after all sensors (higher order number)
scheduler.add(fusion_node).order(1).build()?;
scheduler.run()?;
```

### Mode Comparison

| Feature | Sequential | Parallel |
|---------|------------|----------|
| Predictable Order | **Yes** | Per-priority level |
| Multi-core | No | **Yes** |
| Best Latency | 87-313ns | Variable |
| Certification Ready | **Yes** | No |

## DurationExt and Frequency

HORUS provides ergonomic extension methods for creating `Duration` and `Frequency` values, replacing verbose `Duration::from_micros(200)` calls:

### Duration Helpers

```rust
use horus::prelude::*;

// Microseconds
let budget = 200.us();     // Duration::from_micros(200)
let short = 1.5.us();      // Duration::from_nanos(1500)

// Milliseconds
let deadline = 1.ms();     // Duration::from_millis(1)
let timeout = 0.5.ms();    // Duration::from_micros(500)
```

Works on `u64`, `f64`, and `i32` literals.

### Frequency Type

The `.hz()` method creates a `Frequency` that auto-derives timing parameters:

```rust
use horus::prelude::*;

let freq = 100.hz();

freq.value()            // 100.0 Hz
freq.period()           // 10ms (1/frequency)
freq.budget_default()   // 8ms  (80% of period)
freq.deadline_default() // 9.5ms (95% of period)
```

Use `Frequency` with the node builder's `.rate()` method to auto-configure RT timing:

```rust
// Auto-derives budget (80% period) and deadline (95% period)
// Also auto-marks the node as RT
scheduler.add(motor_ctrl)
    .order(0)
    .rate(500.hz())   // period=2ms, budget=1.6ms, deadline=1.9ms
    .on_miss(Miss::Skip)
    .build()?;
```

| Method | Returns | Description |
|--------|---------|-------------|
| `.us()` | `Duration` | Microseconds |
| `.ms()` | `Duration` | Milliseconds |
| `.hz()` | `Frequency` | Frequency in Hz |
| `freq.value()` | `f64` | Frequency in Hz |
| `freq.period()` | `Duration` | 1/frequency |
| `freq.budget_default()` | `Duration` | 80% of period |
| `freq.deadline_default()` | `Duration` | 95% of period |
