# Hardware Discovery

> **Planned Feature**: A comprehensive Rust-level hardware discovery API (`HardwareDiscovery`, bus scanners, device database) is planned but not yet implemented. This page describes the current hardware interaction patterns and the planned API design.

## Current State

HORUS currently provides hardware interaction through **custom Python nodes** that you write to interface with your specific hardware. The HORUS Node API handles scheduling, pub/sub, and lifecycle management while you write the hardware-specific code:

```python
from horus import Node, Scheduler, Topic, Imu
import time

imu_topic = None

def init(node):
    global imu_topic
    imu_topic = Topic(Imu)

def imu_tick(node):
    # Your hardware reading code here (I2C, serial, etc.)
    # For example, reading from an MPU6050 via smbus:
    imu_data = Imu(
        accel_x=0.0, accel_y=0.0, accel_z=9.81,
        gyro_x=0.0, gyro_y=0.0, gyro_z=0.0
    )
    imu_topic.send(imu_data)

node = Node(name="imu_reader", tick=imu_tick, init=init, rate=100)
scheduler = Scheduler()
scheduler.add(node, order=0)
scheduler.run()
```

Hardware-specific libraries (e.g., `smbus2` for I2C, `pyserial` for serial) are used alongside HORUS nodes.

### Node/Topic Discovery

The `horus monitor` command provides runtime discovery of **running nodes and active topics** (not hardware devices):

```bash
# See all running nodes and topics
horus monitor --tui

# Or use the web interface
horus monitor
```

The monitor shows:
- Active nodes with status and metrics
- Shared memory topics with subscriber/publisher counts
- Network connections between nodes

See [Monitor Guide](/development/monitor) for details.

## Planned: Hardware Discovery API

The following API is planned for a future release. It will enable automatic detection and identification of connected devices from Rust code.

### Planned Rust API

```rust
// Planned API — not yet implemented
use horus::prelude::*;

// Create discovery instance
let discovery = HardwareDiscovery::new()?;

// Detect platform
let platform = discovery.platform();
println!("Platform: {:?}", platform);  // e.g., RaspberryPi4, JetsonOrin

// Scan all hardware
let report = discovery.scan_all();
println!("{}", report.summary());

// Access results
for device in &report.usb_devices {
    println!("USB: {} (VID:{:04X} PID:{:04X})",
        device.product.as_deref().unwrap_or("Unknown"),
        device.vendor_id, device.product_id);
}
```

### Planned Bus Scanners

Individual bus scanners for specific hardware interfaces:

| Scanner | Description |
|---------|-------------|
| `I2cDiscovery` | Enumerate I2C buses and probe device addresses |
| `SpiDiscovery` | Enumerate SPI buses and chip selects |
| `CanDiscovery` | Discover CAN interfaces and state |
| `GpioDiscovery` | Enumerate GPIO chips and line usage |
| `PwmDiscovery` | Find PWM chips and channels |
| `CameraDiscovery` | Detect cameras and supported formats |
| `BluetoothDiscovery` | Find Bluetooth adapters and paired devices |
| `NetworkDiscovery` | Enumerate network interfaces |

### Planned Device Database

A built-in database of robotics device VID/PID mappings for automatic identification of:
- Motor controllers (ODrive, VESC, RoboClaw)
- LiDARs (RPLIDAR, Velodyne, Livox)
- Depth cameras (RealSense, ZED, Azure Kinect)
- IMUs, GPS modules, CAN adapters
- Microcontrollers (Arduino, Teensy, ESP32)

## Best Practices (Current)

1. **Write custom nodes** for your hardware using HORUS's Node API with Python hardware libraries
2. **Use the monitor** to verify nodes are running and topics are flowing
3. **Check device paths** before starting: `ls /dev/ttyUSB*` for serial, `ls /dev/video*` for cameras
4. **Use typed messages** (Imu, LaserScan, CmdVel) for cross-language compatibility with Rust nodes

```bash
# Verify hardware is connected before running
ls /dev/ttyUSB*     # Serial devices
ls /dev/video*      # Cameras
ls /dev/i2c-*       # I2C buses
```
