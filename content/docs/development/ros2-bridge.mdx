# ROS2 Bridge

> **Planned Feature**: The HORUS ROS2 Bridge is planned but not yet implemented. This page describes the intended design for runtime interoperability between HORUS and ROS2. Current HORUS applications run standalone without ROS2 dependencies.

## Current State

HORUS does not currently have a ROS2 bridge. The framework operates independently with its own:
- **Shared memory IPC** for inter-node communication
- **Network transport** for cross-machine messaging
- **Message types** defined in `horus_library`

### Network Transport

HORUS currently uses mDNS/DNS-SD for network discovery. A Zenoh-based transport layer for ROS2 bridging is planned but not yet implemented — no Zenoh-related configuration types exist in the codebase yet.

The bridge would:
1. Connect to the ROS2 network via Zenoh (using the zenoh-ros2-dds-bridge protocol)
2. Discover ROS2 topics, services, and actions
3. Translate messages between CDR (ROS2) and HORUS formats
4. Publish/subscribe on HORUS shared memory topics

### Planned CLI

```bash
# Planned commands — not yet available
horus bridge ros2 --topics /scan,/odom,/cmd_vel
horus bridge ros2 --all
horus bridge ros2 --direction in --topics /scan
```

### Planned Topic Mapping

| ROS2 Topic | HORUS Topic |
|------------|-------------|
| `/scan` | `scan` |
| `/robot/odom` | `robot.odom` |
| `/cmd_vel` | `cmd_vel` |

Key differences:
- ROS2 uses `/` (forward slash) as separator
- HORUS uses `.` (dot) as separator
- Leading `/` would be stripped

### Planned Message Type Mapping

The bridge would map between standard ROS2 messages and HORUS types:

| ROS2 Message | HORUS Type |
|-------------|------------|
| `geometry_msgs/Twist` | `Twist` |
| `sensor_msgs/LaserScan` | `LaserScan` |
| `sensor_msgs/Imu` | `Imu` |
| `nav_msgs/Odometry` | `Odometry` |
| `geometry_msgs/PoseStamped` | `Pose2D` |

## Migrating from ROS2

While waiting for the bridge, you can migrate ROS2 functionality to HORUS directly:

### ROS2 Subscriber → HORUS Topic

**ROS2 (Python):**
```python
import rclpy
from sensor_msgs.msg import LaserScan

def scan_callback(msg):
    print(f"Min range: {min(msg.ranges)}")

node.create_subscription(LaserScan, '/scan', scan_callback, 10)
```

**HORUS equivalent (Python):**
```python
from horus import Node, run

def controller(node):
    if node.has_msg("scan"):
        scan = node.get("scan")
        print(f"Scan data: {scan}")

node = Node(name="scanner", subs=["scan"], tick=controller, rate=10)
run(node)
```

### ROS2 Publisher → HORUS Topic

**ROS2 (Python):**
```python
from geometry_msgs.msg import Twist

msg = Twist()
msg.linear.x = 1.0
publisher.publish(msg)
```

**HORUS equivalent (Python):**
```python
from horus import Node, run

def drive(node):
    node.send("cmd_vel", {"linear": 1.0, "angular": 0.0})

node = Node(name="driver", pubs=["cmd_vel"], tick=drive, rate=10)
run(node)
```

### Key Differences from ROS2

| Feature | ROS2 | HORUS |
|---------|------|-------|
| **IPC** | DDS (network-based) | Shared memory (~85ns) |
| **Message format** | CDR serialized | Zero-copy POD structs |
| **Discovery** | DDS discovery | Shared memory segments |
| **Language** | C++/Python | Rust/Python |
| **Build system** | colcon/CMake | cargo/horus.yaml |
| **Package format** | .deb/.rpm | HORUS registry |

## Requirements for Future Bridge

When implemented, the bridge will likely require:

- HORUS with Zenoh transport feature
- ROS2 Humble, Jazzy, or Rolling
- Zenoh ROS2 DDS bridge plugin (`zenoh-plugin-ros2dds`)
